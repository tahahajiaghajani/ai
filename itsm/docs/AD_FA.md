# ورود با حساب سازمانی (Active Directory) و ورود خودکار ویندوز

این راهنما برای تیم Active Directory و مدیر سامانه در بانک است: چه چیزی در AD ساخته شود، گواهی LDAPS، نگاشت گروه‌ها به نقش‌ها، ورود خودکار ویندوز (Kerberos یا IIS)، سیاست نشست پیشنهادی برای بانک و عیب‌یابی.

در سامانه سه راه ورود هست:

1. **ورود خودکار با حساب ویندوز** — رایانهٔ عضو دامنه بی‌آنکه چیزی تایپ شود وارد می‌شود (Kerberos).
2. **ورود با حساب سازمانی** — نام کاربری و گذرواژهٔ دامنه (`ali`، `CORP\ali` یا `ali@corp.bank.ir`).
3. **ورود محلی** (ایمیل و رمز عبور) — برای حساب‌های اضطراری مدیران (break-glass)؛ برای بقیه با سیاست بسته می‌شود.

هر سه به همان نشست عادی سامانه می‌رسند. نشستی که از راه فهرست کاربران یک سازمان باز شود فقط به همان سازمان می‌رسد (نه به سازمان دیگر و نه به کنسول مدیریت سامانه).

## ۱. آنچه در Active Directory ساخته می‌شود

### حساب خدمت فقط‌خواندنی

سامانه با این حساب کاربر را در AD پیدا می‌کند و گروه‌هایش را می‌خواند؛ هیچ‌گاه چیزی در AD نمی‌نویسد. گذرواژهٔ هر کاربر فقط برای «bind» به خود کنترل‌کنندهٔ دامنه فرستاده می‌شود و هرگز ذخیره یا ثبت نمی‌شود.

```powershell
New-ADUser -Name "svc-kariz-ldap" -SamAccountName "svc-kariz-ldap" `
  -UserPrincipalName "svc-kariz-ldap@corp.bank.ir" `
  -Path "OU=Service Accounts,DC=corp,DC=bank,DC=ir" `
  -AccountPassword (Read-Host -AsSecureString "Password") `
  -Enabled $true -PasswordNeverExpires $true -CannotChangePassword $true
```

- عضویت پیش‌فرض Domain Users برای خواندن ویژگی‌های کاربران و گروه‌ها کافی است؛ هیچ حق نوشتنی لازم نیست.
- ورود تعاملی را برای این حساب ببندید (GPO: «Deny log on locally» و «Deny log on through Remote Desktop Services») و گزینهٔ «Account is sensitive and cannot be delegated» را روشن کنید.
- گذرواژهٔ آن در سامانه با رمزنگاری سکوی سامانه نگه داشته می‌شود و هرگز به مرورگر برنمی‌گردد. پس از عوض‌کردن گذرواژه در AD، آن را در منبع هم عوض کنید.
- ویژگی‌های `msDS-User-Account-Control-Computed` و `msDS-UserPasswordExpiryTimeComputed` (برای تشخیص قفل و انقضای گذرواژه) برای کاربران احرازشده خواندنی است.

### گروه‌ها

نام‌ها پیشنهادی است؛ هر نامی که بانک بخواهد درست است (نگاشت با DN یا CN گروه انجام می‌شود):

| گروه AD | کاربرد |
|---|---|
| `Kariz-Users` | (اختیاری) فقط اعضای این گروه بتوانند وارد شوند — با پالایهٔ کاربران |
| `Kariz-Agents` | کارشناسان پشتیبانی → نقش `agent` و گروه میز خدمت |
| `Kariz-Agents-Network`، `Kariz-Agents-Desktop`، … | تیم‌ها؛ درون `Kariz-Agents` (گروه تودرتو) و هر کدام به گروه ITSM خودش |
| `Kariz-Admins` | مدیران سامانه → نقش `tenant_admin` (با دقت تأیید کنید) |
| `Kariz-Auditors` | ممیزان → نقش `auditor` |

```powershell
New-ADGroup -Name "Kariz-Agents" -GroupScope Global -GroupCategory Security -Path "OU=Groups,DC=corp,DC=bank,DC=ir"
New-ADGroup -Name "Kariz-Agents-Network" -GroupScope Global -GroupCategory Security -Path "OU=Groups,DC=corp,DC=bank,DC=ir"
Add-ADGroupMember -Identity "Kariz-Agents" -Members "Kariz-Agents-Network"
```

عضویت تودرتو با `LDAP_MATCHING_RULE_IN_CHAIN` (`1.2.840.113556.1.4.1941`) خوانده می‌شود: کسی که عضو `Kariz-Agents-Network` است، عضو `Kariz-Agents` هم شمرده می‌شود.

## ۲. گواهی LDAPS

گذرواژه‌ها فقط روی اتصال رمزنگاری‌شده فرستاده می‌شوند: **LDAPS (درگاه ۶۳۶)** یا **StartTLS (درگاه ۳۸۹)**. اتصال بدون رمزنگاری فقط با گزینهٔ صریح «بدون رمزنگاری — فقط برای آزمایش» ممکن است و در بانک نباید به کار رود.

1. اگر AD CS (مرجع صدور سازمانی) دارید، کنترل‌کننده‌های دامنه گواهی «Domain Controller» یا «Kerberos Authentication» را خودکار می‌گیرند و LDAPS روی ۶۳۶ کار می‌کند.
2. گواهی ریشهٔ مرجع صدور را با قالب **Base-64 (.cer)** بگیرید: `certlm.msc` ← Trusted Root Certification Authorities ← گواهی ریشهٔ بانک ← Export ← «Base-64 encoded X.509». متن آن (از `-----BEGIN CERTIFICATE-----` تا `-----END CERTIFICATE-----`) را در «گواهی ریشهٔ سازمان (PEM)» منبع بچسبانید. اگر مرجع میانی دارید، آن را هم زیر ریشه بچسبانید.
3. نشانی کنترل‌کننده‌ها را با **نام کامل (FQDN)** بنویسید، همان نامی که در گواهی آمده است (`ldaps://dc1.corp.bank.ir:636`)، نه با IP.
4. آزمایش از سرور سامانه: `Test-NetConnection dc1.corp.bank.ir -Port 636` و در `ldp.exe`: Connection ← Connect ← پورت ۶۳۶ و تیک SSL.

سامانه گواهی سرور را با همین ریشه و نام سرور می‌سنجد؛ گواهی منقضی، گواهی‌ای که مرجع دیگری امضا کرده یا نامی که با گواهی نمی‌خواند رد می‌شود و علت آن در «آزمایش ورود» و گزارش ورودها نوشته می‌شود.

> bind سادهٔ روی LDAPS با سیاست‌های «LDAP signing» و «channel binding» مایکروسافت (ADV190023) سازگار است؛ این سیاست‌ها bind بدون رمزنگاری روی ۳۸۹ را می‌بندند که سامانه به کار نمی‌برد.

## ۳. تنظیم منبع در سامانه

تنظیمات ← اتصال‌ها و یکپارچه‌سازی ← **فهرست کاربران (LDAP و SCIM)** ← منبع LDAP:

| فیلد | نمونه | توضیح |
|---|---|---|
| نشانی LDAP | `ldaps://dc1.corp.bank.ir:636` | کنترل‌کنندهٔ اصلی |
| کنترل‌کننده‌های دامنهٔ دیگر | `ldaps://dc2.corp.bank.ir:636` | هر خط یکی؛ اگر اصلی پاسخ ندهد به ترتیب امتحان می‌شوند |
| رمزنگاری اتصال | LDAPS | یا StartTLS برای نشانی‌های `ldap://` |
| گواهی ریشهٔ سازمان | `-----BEGIN CERTIFICATE-----…` | بند ۲ |
| حساب اتصال (Bind DN) | `CN=svc-kariz-ldap,OU=Service Accounts,DC=corp,DC=bank,DC=ir` | حساب خدمت |
| ریشهٔ جست‌وجو | `DC=corp,DC=bank,DC=ir` | |
| پالایهٔ کاربران | `(&(objectCategory=person)(objectClass=user))` | پایین را ببینید |
| نام ورود | sAMAccountName | نامی که بدون دامنه نوشته می‌شود |
| دامنه‌ها | `CORP`، `corp.bank.ir` | نام NetBIOS و DNS؛ برای `CORP\ali` و `ali@corp.bank.ir` |
| گروه‌های تودرتو | روشن | |
| ساخت عضو در نخستین ورود | روشن | خاموش: فقط کسانی که پیش‌تر همگام شده‌اند |
| نقش اعضای تازه | `requester` | |
| زمان انتظار هر سرور | ۱۰ ثانیه | |

پالایه‌های سودمند:

```text
# فقط حساب‌های فعال
(&(objectCategory=person)(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))
# فقط اعضای Kariz-Users (مستقیم یا تودرتو)
(&(objectCategory=person)(objectClass=user)(memberOf:1.2.840.113556.1.4.1941:=CN=Kariz-Users,OU=Groups,DC=corp,DC=bank,DC=ir))
```

نسخهٔ وب فقط به سرورهای LDAP با نشانی عمومی وصل می‌شود؛ نسخهٔ سرور و برنامهٔ ویندوز به کنترل‌کننده‌های شبکهٔ داخلی (نصب درون‌سازمانی با `ITSM_DIRECTORY_LAN=1`).

سپس:

1. در زبانهٔ **«ورود و SSO»** ← «آزمایش ورود»، نام یک کاربر (بی‌گذرواژه) را بزنید: اتصال، حساب خدمت، پیدا شدن کاربر، وضعیت حساب، گروه‌ها (با تودرتوها) و نقش‌هایی که می‌گیرد نمایش داده می‌شود.
2. «نگاشت‌ها» را ببینید: هر گروه AD در دامنه پیدا شد؟ چند نفر را در بر می‌گیرد؟
3. **«تأیید منبع با دسترسی من»** را بزنید (برای این کار هویت دوباره پرسیده می‌شود). ساخت عضوها و نقش‌ها با دسترسی همین مدیر انجام می‌شود.
4. «ورود با حساب سازمانی» را روشن کنید.

اعضایی که پیش‌تر با ایمیل و رمز محلی ساخته شده‌اند، خودبه‌خود به حساب سازمانی پیوند نمی‌خورند (ایمیل در AD گواه مالکیت آن حساب نیست): یک بار «پیش‌نمایش» و «اعمال» همگام‌سازی را بزنید تا پیوندها را ببینید و تأیید کنید؛ پس از آن با حساب سازمانی وارد می‌شوند. حساب مدیر سامانه و حسابی که عضو سازمان دیگری است هرگز با حساب سازمانی وارد نمی‌شود.

در نصبی که چند سازمان دارد، دامنه‌ها میان سازمان‌ها جست‌وجو نمی‌شوند: کاربران باید از **پیوند ورود سازمان** (`/login?dir=<شناسهٔ منبع>`، در زبانهٔ «ورود خودکار ویندوز») وارد شوند.

## ۴. نگاشت گروه‌ها به نقش، گروه، واحد و فضای کاری

«نگاشت گروه‌ها» فهرستی JSON است؛ هر گروه AD (DN یا CN) می‌تواند به نقش ITSM، گروه ITSM، واحد سازمانی و فضای کاری برسد:

```json
[
  { "source": "CN=Kariz-Agents,OU=Groups,DC=corp,DC=bank,DC=ir", "role": "agent", "group_id": "<گروه میز خدمت>" },
  { "source": "CN=Kariz-Agents-Network,OU=Groups,DC=corp,DC=bank,DC=ir", "group_id": "<گروه شبکه>" },
  { "source": "Kariz-Admins", "role": "tenant_admin" },
  { "source": "CN=Kariz-HR,OU=Groups,DC=corp,DC=bank,DC=ir", "role": "hr_agent", "workspace_id": "<فضای کاری منابع انسانی>" },
  { "source": "CN=Branch-Tehran,OU=Groups,DC=corp,DC=bank,DC=ir", "unit_id": "<واحد شعبهٔ تهران>" }
]
```

قاعده‌ها:

- **هیچ نقشی بی‌صدا داده نمی‌شود.** نقش‌ها، فضاهای کاری و گروه‌هایی که خودشان نقش یا فضای کاری می‌دهند فقط وقتی در ورود داده می‌شوند که «نقش‌های نگاشت‌شده خودکار داده شود» روشن باشد **و** نگاشت‌ها همان باشند که مدیر تأیید کرده است. با هر تغییر نگاشت‌ها (یا نقش پیش‌فرض و عضویت پایه)، تا تأیید دوباره، نقش‌ها «در انتظار تأیید» می‌مانند و در گزارش ورودها دیده می‌شوند.
- عضو تازه نقش پیش‌فرض (درخواست‌دهنده) را می‌گیرد و نقش‌های تأییدشدهٔ گروه‌هایش را هم.
- اگر کسی از گروه AD بیرون برود، نقش، گروه و فضای کاری‌ای که آن نگاشت داده بود در ورود بعدی گرفته می‌شود (نقش پیش‌فرض می‌ماند).
- در هر ورود نام، ایمیل، تلفن، سمت، واحد (از department یا نگاشت) و مدیر مستقیم (از manager) به‌روز می‌شود.
- همگام‌سازی دوره‌ای (پیش‌نمایش و اعمال) همین نگاشت‌ها را به کار می‌برد و اجرای زمان‌بندی‌شده هم نقش‌ها را فقط برای نگاشت‌های تأییدشده می‌دهد (منبعی که پیش از این نسخه تأیید شده، یک بار دوباره تأیید شود)؛ کسی که در AD غیرفعال یا حذف شود، در همگام‌سازی بعدی غیرفعال می‌شود و نشست‌هایش بسته می‌شود.

## ۵. ورود خودکار ویندوز (SSO)

### راه ۱ — Kerberos روی خود سرور (نسخهٔ سرور ویندوز)

پیش‌نیازها:

- سرور ویندوز سامانه عضو دامنه باشد؛ سرویس سامانه با یک حساب دامنه (مثلاً `BANK\svc-kariz-web`) یا Network Service اجرا شود.
- ماژول بومی `node-expose-sspi` (همراه بستهٔ نصب نسخهٔ سرور؛ فقط وقتی بار می‌شود که این حالت روشن باشد).
- رکورد DNS از نوع **A** برای نام سامانه (`kariz.bank.ir`)؛ کاربران سامانه را فقط با همین نام باز کنند (نه IP).

ثبت SPN (در کنترل‌کنندهٔ دامنه، با Domain Admin) — فرمان دقیق برای نام و حساب تنظیم‌شده در زبانهٔ «ورود خودکار ویندوز» منبع نشان داده می‌شود:

```cmd
setspn -Q HTTP/kariz.bank.ir
setspn -S HTTP/kariz.bank.ir BANK\svc-kariz-web
setspn -S HTTP/kariz BANK\svc-kariz-web
```

- فرمان نخست SPN تکراری را پیدا می‌کند؛ SPN تکراری Kerberos را برای همه از کار می‌اندازد (`setspn -X` همهٔ تکراری‌ها را نشان می‌دهد).
- اگر سرویس با Network Service اجرا می‌شود، به‌جای حساب، نام رایانه با `$` را بنویسید (`KARIZ-SRV01$`).
- در حساب سرویس گزینه‌های «This account supports Kerberos AES 128/256 bit encryption» را روشن کنید.
- سامانه به‌طور پیش‌فرض فقط Kerberos را می‌پذیرد؛ NTLM (رایانه‌های بیرون از دامنه) فقط با گزینهٔ «پذیرش NTLM» و برای همان اتصال.

### راه ۲ — IIS جلوی سامانه (پشتیبانی‌شده‌ترین راه)

IIS با Windows Authentication کاربر را می‌شناسد و نام او را در یک سرآیند به سامانه می‌دهد. همهٔ اجزای احراز هویت این راه را مایکروسافت نگه‌داری می‌کند.

1. Windows Authentication را **فقط برای مسیر** `/api/auth/sso` روشن و Anonymous را خاموش کنید؛ بقیهٔ مسیرها Anonymous.
2. با ARR و URL Rewrite درخواست‌ها را به سامانه بفرستید و دو متغیر سرور را تنظیم کنید (در «allowedServerVariables» هم بیفزایید):

```xml
<rule name="kariz" stopProcessing="true">
  <match url="(.*)" />
  <serverVariables>
    <set name="HTTP_X_REMOTE_USER" value="{LOGON_USER}" />
    <set name="HTTP_X_ITSM_PROXY_SECRET" value="<راز مشترک پراکسی>" />
  </serverVariables>
  <action type="Rewrite" url="http://127.0.0.1:3000/{R:1}" />
</rule>
```

3. در منبع: «ورود خودکار ویندوز» = «از راه IIS یا پراکسی معتمد»، «نشانی‌های پراکسی معتمد» = نشانی IIS (اگر روی همان سرور است `127.0.0.1`)، «سرآیند کاربر پراکسی» = `X-Remote-User`، و «راز مشترک پراکسی» را بسازید و در IIS بگذارید.

سرآیند کاربر **فقط** از نشانی‌های فهرست‌شده (نشانی واقعی اتصال TCP، نه `X-Forwarded-For`) و **فقط** همراه راز مشترک پذیرفته می‌شود؛ درخواستی با سرآیند جعلی از نشانی دیگر رد، ثبت و به مدیران گزارش می‌شود.

| | Kerberos روی سرور | IIS جلوی سامانه |
|---|---|---|
| اجزای اضافه | ماژول بومی `node-expose-sspi` (متن‌باز، یک نگه‌دارنده) | IIS، ARR، URL Rewrite (مایکروسافت) |
| نگه‌داری | ثبت SPN برای حساب سرویس سامانه | ثبت SPN برای IIS (همان روش)، تنظیم بازنویسی |
| NTLM | خاموش؛ اختیاری | با تنظیم IIS |
| پیشنهاد بانک | وقتی IIS در کار نیست | **راه پیشنهادی** |

### مرورگرها (Group Policy)

- **Edge و Chrome**: Computer Configuration ← Administrative Templates ← Microsoft Edge / Google Chrome ← HTTP authentication ← «Configure list of allowed authentication servers» (`AuthServerAllowlist`) = `kariz.bank.ir`.
- **Internet Options (برای Edge و Chrome روی ویندوز هم به کار می‌رود)**: «Site to Zone Assignment List» = `https://kariz.bank.ir` ← مقدار `1` (Local intranet).
- **Firefox**: `network.negotiate-auth.trusted-uris` = `https://kariz.bank.ir`.

آزمایش از رایانهٔ کاربر: `klist purge` و سپس باز کردن سامانه؛ `klist` باید بلیت `HTTP/kariz.bank.ir` را نشان دهد.

در صفحهٔ ورود، دکمهٔ «ورود خودکار با حساب ویندوز» هست؛ اگر «تلاش خودکار در صفحهٔ ورود» روشن باشد، سامانه یک بار در هر زبانهٔ مرورگر خودش امتحان می‌کند و اگر نشد فرم ورود را نشان می‌دهد.

### در نسخهٔ سرور ویندوز

نسخهٔ سرور ([SERVER_FA.md](SERVER_FA.md) بخش ۹) هر دو راه را دارد:

- **Kerberos روی خود سرور**: نام سامانه معمولاً `kariz.bank.local` است؛ سرویس `KarizApp` با حساب مجازی اجرا می‌شود، پس SPN روی حساب رایانه ثبت می‌شود (`setspn -S HTTP/kariz.bank.local KARIZ-SRV01$`)، یا روی حساب دامنه‌ای که سرویس را با آن اجرا می‌کنید (`BANK\svc-kariz-web`). بررسی بلیت کار ویندوز است و اتصال خروجی نمی‌خواهد.
- **IIS روی همان سرور**: IIS روی ۴۴۳ و نسخهٔ سرور روی loopback (مثلاً `https://127.0.0.1:8443`) — در بازنویسی بالا همین نشانی را بگذارید؛ «نشانی‌های پراکسی معتمد» منبع = `127.0.0.1`. IIS روی سرور دیگر: نشانی آن باید هم در منبع و هم در `trusted_proxies` فایل `kariz.json` باشد (یک فهرست برای سرآیندهای `X-Forwarded-*`، نشانی کاربر و SSO).
- کنترل‌کننده‌های دامنه باید در فهرست مجاز شبکهٔ بستهٔ سرور باشند (`karizctl allow add dc1.bank.local` یا «سلامت سرور»).
- GPO مرورگرها همان بالاست، با `kariz.bank.local`.

ورود خودکار در نسخهٔ وب (Vercel) و برنامهٔ ویندوز در دسترس نیست؛ «ورود با حساب سازمانی» در برنامهٔ ویندوز وقتی کار می‌کند که رایانه به کنترل‌کنندهٔ دامنه (شبکهٔ داخلی) دسترسی داشته باشد.

## ۶. سیاست نشست پیشنهادی برای بانک

تنظیمات ← **امنیت ورود و نشست‌ها** ← «سیاست» (دکمهٔ «پیشنهاد بانک» این مقدارها را می‌گذارد):

| تنظیم | پیشنهاد | توضیح |
|---|---|---|
| پایان پس از بیکاری | ۱۵ دقیقه | |
| عمر کامل نشست | ۱۰ ساعت | یک روز کاری |
| یک نشست فعال برای هر نفر | روشن | ورود تازه نشست‌های دیگر را می‌بندد |
| تأیید دوبارهٔ هویت برای کارهای حساس | ۱۰ دقیقه | سیاست ورود، تنظیم منبع و نگاشت‌ها، نقش‌ها، نشست دیگران، تغییر رمز اعضا |
| پایان نشست با بستن مرورگر | روشن | |
| ورود محلی | فقط حساب‌های اضطراری | دو حساب مدیر با رمز قوی، در پاکت مهروموم |
| قفل محلی | ۵ تلاش در ۱۵ دقیقه، ۳۰ دقیقه قفل | کمتر از آستانهٔ قفل دامنه (مثلاً ۱۰) تا حدس‌زننده حساب دامنه را قفل نکند |
| تلاش ناموفق از یک نشانی | ۲۰ | در برابر password spraying |

- کوکی نشست همیشه HttpOnly و SameSite است و روی HTTPS خودکار Secure می‌شود؛ `X-Forwarded-Proto` فقط از پراکسی معتمد پذیرفته می‌شود. روی نسخهٔ سرور: `ITSM_COOKIE_SECURE=always`، `ITSM_TRUSTED_PROXIES=<نشانی IIS>` و در صورت نیاز `ITSM_COOKIE_SAMESITE=strict`.
- سخت‌تر کردن سیاست، نشست‌های باز را هم هماهنگ می‌کند (زمان بیکاری و عمر کوتاه‌تر).
- مدیر در «نشست‌های باز» همهٔ نشست‌ها (روش ورود، IP، مرورگر، آخرین فعالیت) را می‌بیند و یکی، همهٔ نشست‌های یک نفر یا همه را می‌بندد؛ هر کس از «حساب کاربری من» از همهٔ دستگاه‌های دیگر خارج می‌شود.

## ۷. گزارش ورودها و هشدارها

- هر تلاش ورود (روش، منبع، IP، نتیجه، علت) در «امنیت ورود و نشست‌ها ← گزارش ورودها» و در زبانهٔ «ورودها»ی منبع ثبت می‌شود؛ گذرواژه‌ها هرگز ثبت نمی‌شوند.
- پیام‌هایی که کاربر می‌بیند هیچ‌گاه نمی‌گویند حسابی هست یا نیست؛ علت دقیق (غیرفعال، منقضی، باید گذرواژه عوض شود) فقط وقتی گفته می‌شود که گذرواژه درست بوده است.
- مدیران سازمان (در برنامه و با ایمیل) خبر می‌گیرند وقتی: یک نام کاربری پس از تلاش‌های ناموفق قفل محلی شود، یک نشانی نام‌های زیادی را امتحان کند، تلاش‌های ناموفق یک منبع زیاد شود، سرور دامنه یا گواهی آن در دسترس نباشد، یا سرآیند پراکسی از نشانی نامعتبر برسد.
- «قفل‌ها»: نام‌ها و نشانی‌های قفل‌شده و «رفع قفل».
