# Jira Service Management (Atlassian) — complete feature catalog

*Research snapshot: 2026-11-07. Primary sources are Atlassian's own cloud documentation (support.atlassian.com, ~550 pages read across Jira Service Management, Assets, Customer Service Management, Atlassian Automation, Rovo, Insights/Analytics, Atlassian Administration), the live Service Collection pricing page, the Jira Service Management Data Center release notes, and a mirror of Atlassian's in-app release notes (Nov 2024 – Nov 2026). Anything not confirmed in a source is marked "(unverified)". Atlassian renamed many concepts in 2025–2026; current names are used, with old names in brackets.*

## Overview

**Positioning.** Jira Service Management (JSM) is Atlassian's ITSM/ESM product built on the Jira platform (work items, workflows, JQL, automation) with a service-desk layer (request types, portal/help center, queues, SLAs, approvals, customers/organizations), a native operations layer inherited from Opsgenie (alerts, on-call, escalations, heartbeats, ChatOps, status pages), a CMDB/asset layer (Assets, Data Manager, Hardware Asset Management), and a pervasive AI layer (Rovo: search, chat, agents, Studio, Request Resolver, Ops Expert, virtual service agent). It is sold as **Atlassian Service Collection** and positioned for "high-velocity" IT, DevOps-integrated incident/change management and any business team (HR, facilities, legal, finance, marketing, sales, design, analytics).

**Packaging (as of Nov 2026).**
- **Service Collection** launched 7 Oct 2025 (Team '25 Europe, Barcelona): one per-agent SKU containing Jira Service Management + **Customer Service Management (CSM)** (new external-support app) + **Assets** (now a standalone "platform app" usable from any Jira app) + **Rovo** (AI). JSM is no longer sold standalone; existing JSM customers are moved to Service Collection at renewal during Atlassian FY2026. Price per agent was kept equal to former JSM pricing. Service Collection also includes the Atlassian platform apps (Home, Goals, Teams, Studio, Search, Chat, Insights, Admin).
- Customer-service features (customer/organization profiles, entitlements, developer escalations) moved out of JSM into CSM for sites created after 10 Oct 2025; older sites keep them in JSM.

Usage limits for Assets objects and VSA conversations also started 16 Oct 2024.
- Services are removed from the Free plan after 31 Jul 2026.
- Usage-based billing: automation is metered in **steps** (not rule runs); extra steps billed at $0.50 per 1,000 (runs that perform no actions stop counting from 5 Nov 2026). **Rovo credit** overage billing starts 3 Dec 2026 (third-party guides quote $0.01/credit — unverified). **CSM AI-agent resolutions** cost $1.00 each from 3 Dec 2026 (volume packs down to $0.85). Extra Assets objects are billed from $0.02/object/month. Admins get 80%/100% usage notifications and can disable extra usage or set spend limits.

**Deployment options.**
- **Cloud** (multi-tenant on AWS; data residency in 12 locations; **Atlassian Government Cloud** (FedRAMP) with AI, chat, VSA and anonymous portals unavailable).
- **Data Center** (self-managed): latest feature line JSM DC 11.x — 11.0 (13 Aug 2025), 11.1 (24 Sep 2025), 11.2 (6 Nov 2025), **11.3 Long Term Support (3 Dec 2025, patched to 11.3.13 in 2026)**; previous LTS 10.3. DC 11.2/11.3 add OpenSearch indexing, OAuth 2.0 app links, service-account REST scopes, JQL resilience, and "Farewell Opsgenie" (removal of the DC Opsgenie integration). **Data Center end of life**: new-customer DC sales ended 30 Mar 2026; existing customers may buy/expand until 30 Mar 2028; all JSM/Jira/Confluence DC subscriptions become read-only 28 Mar 2029 (Bitbucket/Bamboo excluded). DC lacks Rovo/AI, CSM, native status pages, HAM, Insights; DC Assets supports extra import types (DB, LDAP, Jira users/groups).

**Opsgenie sunset.** Opsgenie end of sale 4 Jun 2025; end of support 5 Apr 2027 (access shut off, unmigrated data deleted). An in-app migration tool moves alerting, on-call, integrations, policies, heartbeats etc. into **JSM Operations** (or into Compass for alerting/on-call only). Opsgenie's old "Incident Command Center" video bridge was retired 5 Sep 2024 (replaced by native conference calls/Zoom/Teams); the 2026 "Incident Command Center" is a different, AI-first incident workspace.

**Terminology changes 2025–2026.** projects → *spaces*; issues → *work items*; issue types → *work types*; automation rules → *flows* and components → *steps* (Apr 2026); Atlassian Intelligence → *Rovo/AI*; Rovo Service → *Request Resolver*; Rovo Ops → *Ops Expert*; Service Triage Agent → *Request Router*; Atlassian Analytics → *Insights*; Halp → *Atlassian Assist*; Opsgenie Edge Connector → *Jira Edge Connector (JEC)*; Central Notification Template → *role-based notifications*; notification forwarding → *forwarding rules*; Opsgenie Terraform provider → *Atlassian Operations Terraform provider*; Insight → Assets.

## Module: platform

### Features
- **Work item model (Jira core)** — every record (request, incident, problem, change, PIR, case, hardware work, alert-linked incident) is a Jira *work item* with key (SPACE-123), work type, status, resolution, priority, reporter, assignee, labels, components, linked items, attachments, watchers/votes, worklog, comments (internal vs reply-to-customer), history/changelog, and unlimited custom fields; subtasks and parent/child; work item links with typed relationships ("causes", "is caused by", "relates to", custom; HR "Recruitment" link type). [JSM]
- **Request type ↔ work type ↔ workflow chain** — a *request type* (portal-facing form, name, icon, portal group, help text, work category) maps to exactly one *work type*; a work type maps to exactly one workflow per *workflow scheme*; one work type can back many request types and one workflow can back many work types. Changing a work item's work type requires a matching request type. [JSM]
- **Work categories (ITSM practices)** — five built-in categories: Service requests, Incidents, Problems, Changes, Post-incident reviews (plus HR *Cases*). Categories give dedicated sidebar sections, queues, reports and feature behaviour; can be added to any space via Space settings → Features; request types can be assigned/unassigned/moved between categories; "compatible work types" rules. [ITIL 4]
- **Space types & templates** — company-managed vs team-managed spaces (team-managed: simplified per-space fields, workflow rules, approvals, roles). Templates: IT service management (with ITSM Essentials variant), General service management, Customer service management, HR, Facilities, Legal, Finance, Marketing, Analytics, Sales, Design, Blank; sample/demo space; "Create a service space with Rovo" (describe the team → Rovo proposes request types, queues, SLAs, automations, KB articles, Rovo agent config → builds it). Import from CSV in template gallery (2026). Space backgrounds (2026). [JSM]
- **Workflow engine** — statuses (with status categories To Do / In Progress / Done), transitions, conditions, validators, post-functions, screens on transition, approvals attached to statuses, workflow templates, new drag-and-drop workflow editor, team-managed workflow rules; default ITIL workflows ("ISD: Incident Management workflow", change, problem, service request with approval, fulfilment). Portal-visible customer transitions (e.g., Cancel/Escalate/Resolve) bypass validators and screens. "Comment updates reply status" pattern (Waiting for support ↔ Waiting for customer). [JSM]
- **Fields, screens, request forms and work item view** — per request type: request form (portal fields with display names/help text, required flags, hidden fields with preset values) and agent work item view (field layout, tabs, context fields, Customer panel, SLA panel, Assets panel); unsupported/hidden field rules; inline images in Description (2026). "AI-focused work item view" (Resolve with Rovo) at top of the view. [JSM]
- **Forms (formerly ProForma)** — form builder with 200+ templates; Confluence-style editor (columns, tables, headings, rich text); field types: short/long text, paragraph, email, URL, number, date, date-time, time, radio, checkboxes, dropdown, multi-select, cascading dropdown, user picker, Assets object; conditional logic (show/hide sections/fields; *advanced conditional logic* 2026); validation (required, ranges, regex); form fields can be standalone (not Jira custom fields) or *linked* to Jira fields (two-way sync); *data connections* (REST endpoint returning JSON → populate choice lists; ID/label mapping; never hard-deleted); form locations: attach to request type, shareable link to create work items (embeddable in Confluence), recommended forms added to existing work items (internal or external); form states: open for edits / submitted / locked; settings: lock on submit, save PDF snapshot on each submission, recommend to agents, keep open, ignore validation; per-form view restrictions (users/groups, e.g., "Bank details" visible only to Payroll); translations per form with "Available to customers" toggle and primary-language fallback; smart values `{{forms.last.<fieldKey>}}`; automation triggers (form submitted / attached / opened for edits) and actions (attach forms, attach forms with values, change form status, copy forms). Not supported in email/chat/VSA/widget channels. [ProForma]
- **Search and JQL** — basic search, JQL advanced search (fields, operators =, !=, ~, IN, WAS, CHANGED; functions incl. SLA functions `breached()`, `everBreached()`, `paused()`, `running()`, `completed()`, `withinCalendarHours()`, `elapsed()`, `remaining()`; Assets functions `aqlFunction()`, `aqlFunctionWithoutFilterScope()`; customer functions `customerDetail()`, `organizationDetail()`), saved filters, filter subscriptions, list view with inline edit/sort/bulk actions; Rovo natural-language-to-JQL (Jira, unverified for JSM queues) and `/manage-queue` skill generating JQL. ### Implementation notes
- Model the platform as: `space` → `request_type` (portal metadata, category, portal_group, form_id) → `work_type` → `workflow` (statuses with `category` enum {todo, inprogress, done}; transitions with conditions/validators/post-functions; `approval_step` attached to a status). Enforce the 1:1 request-type→work-type and work-type→workflow(per scheme) constraints and validate on work-type change.
- Treat "work category" as a first-class enum that drives sidebar sections, default queues/reports and feature availability; allow a request type to be "unassigned".
- Forms: store form definition as JSON (sections, fields, conditions as expression trees, validations, translations keyed by locale, linked_field_id). Store *submissions* as immutable versions (state machine open→submitted→locked; reopen creates a new version; optional PDF render). Linked fields require bidirectional sync with conflict rules (last write wins + audit). Data connections are server-side fetches with cached choice lists; soft-delete them.
- Automation: implement an event bus (work item, alert, object, approval, SLA, survey, webhook, schedule events) feeding a rule engine; per-run context with smart-value template engine (Mustache-like with dotted paths, functions and list iteration); persist run audit (steps executed, status). Meter **steps executed** (trigger=1, each evaluated condition=1, action=1, branch=1+inner) and skip billing for system steps and no-action runs; enforce concurrency per plan, loop detection (10 rapid self-triggers), per-run limits (65 steps, 5,000 associated items, 999 items per scheduled JQL) and daily processing time quotas. Advanced steps need a durable workflow runtime (timers up to 90 days, wait-for-event correlation keys, parallel join).
- Approvals: approval instances per (work item, status entry) with required-count policy, decision records (approver, decision, comment, channel, timestamp) and idempotent "approve from email" tokens; when approvers are derived from affected services, resolve at status entry and snapshot.
- Customer-facing vs internal comment visibility must be enforced at the API layer, not only the UI (portal API returns only public comments).

### Implementation notes
- Ingestion pipeline: authenticate integration key → select integration config → apply ignore rules → evaluate create/close/ack/note rules in fixed order → render alert template from payload → apply global then team alert policies → dedup on (alias, open) using an atomic upsert (increment count, lastOccurredAt) → create alert + start notification flow. Use idempotency keys and per-tenant rate limiting.
- Notification flow is a state machine per (alert, recipient): compute recipients (explicit responders override team routing) → routing rule → escalation timers (scheduled jobs keyed by alert id, cancelled on ack/close) → per-user notification rules → contact-method dispatch with aggregation windows (SMS 1 min, voice 4 min) → delivery receipts into activity log. Policies (delay/restart/auto-close) wrap this machine and must reset timers on dedup.
- On-call calculation: materialise schedule timelines by expanding rotations (with time zones and DST) and applying override and forwarding layers to produce the Final layer; store historical final layer for reporting.
- Grouping: streaming clustering over embeddings of message+description plus exact-match keys (service/integration/tags) inside a time window; groups are durable entities with membership edits (remove alert) and an LLM-generated title/summary; signal/noise = per-tenant classifier trained on historical outcomes with human feedback labels.

## Module: slm

### Features
- **SLA metrics (named SLAs)** — space admins define any number of named SLAs per service space (e.g., *Time to first response*, *Time to resolution*; ITSM template adds *Time to close after resolution* and *Time to approve normal change*); each new SLA name creates a site-wide custom field of type *SLA CustomField Type* (name cannot be changed after creation; Jira admins can "Clean up" unused SLA metric fields under Apps → Jira Service Management → Configuration). - **Multi-cycle SLAs** — when a start event happens again after a stop event a new *cycle* starts (e.g., reopened requests, each customer comment restarting "time to respond"); completed cycles are immutable; JQL and reports evaluate the last/ongoing cycle or any cycle (`everBreached()`). [JSM]
- **Goals** — ordered list of goals per SLA (up to 90 goals per SLA in cloud; raised from 30 in Dec 2023); each goal = *Apply to work items* JQL (e.g., `"Ticket category" = Incidents`), *time target* (e.g., `4h 30m`; may be left empty = track without target) and *calendar*; work items are matched top-to-bottom, first match wins; a catch-all "All remaining work items" goal at the bottom. [JSM]
- **Priority-grouped goals** — under one goal's JQL, add per-priority time targets and calendars (each priority acts as `AND priority = X`), with an *All remaining priorities* catch-all (also matches no priority); a grouped goal counts as one goal, so capacity becomes 90 × number of priorities (e.g., 450 targets with 5 priorities). ### Implementation notes
- Model `sla_metric(id, space_id, name, display_format, portal_visible)`, `sla_condition(metric_id, kind{start|pause|stop}, event_type, param)`, `sla_goal(metric_id, order, jql, calendar_id, target_minutes|null)`, `sla_goal_priority(goal_id, priority_id|REMAINING, target_minutes, calendar_id)`, `sla_calendar(tz, weekly_slots[], holidays[])` and per work item `sla_cycle(work_item_id, metric_id, started_at, stopped_at, paused_intervals[], goal_id, target_minutes, breached_at, met)`.
- Compute elapsed time as business-time over the calendar (convert to UTC intervals, subtract pauses and non-working time) — precompute a calendar "working-minute index" per time zone/day for O(1) interval sums; store projected `breach_at` per ongoing cycle so queue sorting, `remaining()` JQL and *threshold breached* triggers become indexed lookups plus a timer wheel/scheduled job.
- Re-evaluate the goal on every relevant field change (priority, request type, customer detail): carry elapsed time into the newly matched goal; record goal changes in history.
- Event-sourced recalculation: keep the work item's change history so an edited SLA can be recomputed deterministically for ongoing cycles; never rewrite completed cycles; expose an admin "recalculate" job with throttling.
- First-match goal semantics with a catch-all; validate JQL on save and warn about overlapping goals; cap goals (90) and per-priority sub-targets.

### Implementation notes
- Core store: `schema`, `object_type(parent_id, abstract, inherit_attributes, label_attribute_id)`, `attribute(type, ref_object_type_id, ref_type_id, min_card, max_card, unique, regex, suffix, include_children, aql_filter)`, `object(schema_id, type_id, key, label)`, `attribute_value(object_id, attribute_id, value_text|num|date|bool|ref_object_id|user_id|group_id|status_id, ordinal)` (EAV with typed columns) plus a denormalised search index (OpenSearch) per object for AQL. ### Implementation notes
- Use one asset table with typed classes (hardware, model, stockroom, stock rule, depreciation rule) sharing the CMDB store; keep *asset status* separate from *work item status*, with automation mapping work outcomes to asset status transitions (e.g., Ship completed → In use; Return completed → In stock).

### Implementation notes
- Routing pipeline: on trigger events → classify request (LLM/embedding classifier against team or service "routing context" descriptions, return confidence) → set team (or default team below threshold) → compute eligible agents = team members ∩ on-shift (expand recurring schedules in agent time zone) ∩ available → pick argmin(utilization) with deterministic tie-break (oldest last-assignment) → assign or recommend; log the decision with factors for audit and tuning.
- Utilization must be recomputed incrementally on assignment/resolution events; store per (agent, team) open counts and capacity; expose thresholds as config.
- Forecasting: daily seasonal time-series model per team (e.g., Holt-Winters/Prophet-style with weekday seasonality) over created-item counts, plus queueing estimate (Erlang-C or throughput per agent) for required agents; persist forecasts with confidence intervals.
- Schedules: store rule-based recurrences (RRULE) with IANA time zones; materialise shifts for a rolling window; CSV import validates all rows first and supports partial or all-or-nothing modes by role.

### Implementation notes
