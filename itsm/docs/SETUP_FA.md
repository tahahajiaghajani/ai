# راه‌اندازی «کاریز»: Supabase، Vercel و نسخهٔ ویندوز

این راهنما قدم‌به‌قدم است. هر قدم نام صفحه و دکمه را همان‌طور که روی صفحه نوشته شده (انگلیسی، داخل `این علامت`) می‌آورد، می‌گوید چه بنویسید و با «**باید ببینید:**» تمام می‌شود. اگر چیزی که می‌بینید با آن یکی نبود، جلوتر نروید و به جدول رفع اشکال (بخش ۹) سر بزنید.

برچسب‌های داشبوردها از مستندات رسمی Supabase و Vercel در آبان ۱۴۰۵ (نوامبر ۲۰۲۶) برداشته شده‌اند. این سرویس‌ها گاهی نام دکمه‌ها را عوض می‌کنند؛ اگر برچسبی کمی فرق داشت، نزدیک‌ترین گزینه با همان معنا را بزنید.

> نام برنامه «کاریز» (Kariz) است و همه‌جا از `src/shared/constants.ts` خوانده می‌شود. در این راهنما نام پروژه‌ها را `itsm` می‌گذاریم؛ نام پروژه‌های Supabase و Vercel در کار برنامه اثری ندارد.

## برنامه چطور کنار هم قرار می‌گیرد

«کاریز» پروژه‌ای **مستقل** در پوشهٔ `itsm` همین مخزن است. کد، پایگاه داده و تنظیماتش با پروژه‌های دیگر مخزن مشترک نیست.

| بخش | کجا اجرا می‌شود | داده کجاست |
|---|---|---|
| **نسخهٔ وب** (رایانه و گوشی) | یک پروژهٔ Vercel با `Root Directory` = `itsm` | یک پروژهٔ Supabase (PostgreSQL) |
| **نسخهٔ ویندوز** | رایانهٔ کاربر، با یک فایل نصب | پایگاه دادهٔ داخلی خود برنامه، هم‌گام با Supabase |

- مرورگر و گوشی کاربر **فقط با دامنهٔ خود برنامه** حرف می‌زنند. فقط سرور Vercel به Supabase وصل می‌شود. کلید Supabase در مرورگر نیست.
- همهٔ جدول‌ها با پیشوند `sm_` ساخته می‌شوند. RLS روی همه روشن است و هیچ قانون دسترسی ندارند؛ یعنی کلیدهای عمومی Supabase (`anon` و `authenticated`) به هیچ جدولی دسترسی ندارند.
- پایگاه داده (۵۳۰ جدول، ۸۴ مرحله) **پیش از اولین درخواست** ساخته می‌شود: در ساخت Vercel (وقتی `DATABASE_URL` گذاشته شده باشد) یا با یک دستور از هر رایانه (`scripts/migrate-db.mts`). اگر هیچ‌کدام نشد، خود برنامه مرحله‌ها را چند ثانیه‌ای در پس‌زمینهٔ درخواست‌ها اجرا می‌کند و تا تمام نشده صفحهٔ «آماده‌سازی پایگاه داده» را با درصد پیشرفت نشان می‌دهد؛ هیچ درخواستی روی پایگاه دادهٔ نیمه‌کاره پاسخ داده نمی‌شود (`AUTO_MIGRATE`). همین مرحله‌ها برای اجرای دستی هم آماده‌اند: بخش‌های پوشهٔ [`supabase/manual`](../supabase/manual) (قدم ۱-۵).
- ساخت برنامه (`build`) بدون هیچ متغیری انجام می‌شود. برای اجرا فقط `DATABASE_URL` لازم است.

## ۰. پیش از شروع

این‌ها را آماده کنید. کل کار حدود ۳۰ دقیقه طول می‌کشد.

1. **حساب GitHub** که مالک مخزن `tahahajiaghajani/ai` است، و کد ITSM در شاخهٔ `main` آن ادغام شده باشد (پوشهٔ `itsm` در `main` دیده شود).
2. **فیلترشکن** برای باز کردن داشبورد Supabase و Vercel از ایران. فقط خود شما برای این تنظیمات به آن نیاز دارید. کاربران برنامه فیلترشکن لازم ندارند.
3. یک **مدیر رمز** (مثل Bitwarden) یا دفترچه‌ای امن. در این راهنما سه رمز می‌سازید که باید جایی نگه دارید: رمز پایگاه داده، `APP_SECRET` و `CRON_SECRET`.
4. ایمیلی که می‌خواهید با آن **مدیر کل سامانه** باشید.

> پرداخت پلن‌های پولی Supabase و Vercel کارت غیرایرانی می‌خواهد. همهٔ این راهنما با پلن‌های رایگان انجام می‌شود.

**باید ببینید:** در GitHub، در شاخهٔ `main` مخزن `ai`، پوشهٔ `itsm` و داخل آن فایل‌های `vercel.json`، `package.json` و `supabase/schema.sql` هست.

## ۱. پایگاه داده (Supabase)

### ۱-۱. ورود به Supabase

1. [supabase.com/dashboard](https://supabase.com/dashboard) را باز کنید.
2. اگر حساب ندارید `Sign up` را بزنید و با `Continue with GitHub` یا ایمیل حساب بسازید. اگر دارید `Sign in`.

**باید ببینید:** صفحهٔ `Projects` یا فهرست سازمان‌ها (`Organizations`).

### ۱-۲. سازمان (Organization)

اگر از قبل سازمانی در Supabase دارید (مثلاً سازمان پروژه‌های دیگر همین مخزن)، می‌توانید از همان استفاده کنید و به قدم بعد بروید.

1. `New organization` را بزنید.
2. `Name`: یک نام دلخواه، مثلاً `itsm`.
3. `Type`: `Personal`.
4. `Plan`: `Free - $0/month`.
5. `Create organization`.

> پلن رایگان روی هم **دو پروژهٔ فعال** اجازه می‌دهد، در همهٔ سازمان‌هایی که شما مالک یا مدیرشان هستید. اگر دو پروژهٔ فعال دیگر دارید، فرم ساخت پروژه به‌جای فیلدها هشدار محدودیت نشان می‌دهد. یکی را `Pause` یا حذف کنید، یا پلن را ارتقا دهید. پروژهٔ متوقف‌شده شمرده نمی‌شود.

**باید ببینید:** صفحهٔ سازمان با دکمهٔ `New project`.

### ۱-۳. ساخت پروژه

1. در سازمان، `New project` را بزنید.
2. `Project name`: بنویسید `itsm`.
3. `Database password`: روی پیوند `Generate a password` بزنید. رمزی از حرف و عدد ساخته می‌شود که نویسهٔ خاص ندارد و در نشانی اتصال مشکلی ایجاد نمی‌کند. **همین حالا آن را در مدیر رمز ذخیره کنید.**
   - اگر خودتان رمز می‌نویسید و نویسه‌هایی مثل `@ : / # % + ? & =` یا فاصله دارد، پیام `Note: If using the Postgres connection string, you will need to percent-encode the password` می‌آید. در قدم ۱-۴ می‌گوییم چه کنید.
4. `Region`: اگر گزینهٔ `Need a specific region?` یا بخش `Specific regions` هست، **`Central EU (Frankfurt)`** (`eu-central-1`) را انتخاب کنید. اگر فقط منطقه‌های کلی دیده می‌شوند (`Americas`، `Europe`، `APAC`)، `Europe` را بزنید.

   > **مهم‌ترین تنظیم سرعت:** سرور Vercel این برنامه در فرانکفورت (`fra1`، در `itsm/vercel.json`) اجرا می‌شود و پایگاه داده هم باید در فرانکفورت (`eu-central-1`) باشد. هر صفحه چند ده پرسش به پایگاه داده می‌فرستد؛ اگر این دو در دو قارهٔ مختلف باشند (مثلاً پایگاه داده در آمریکا)، هر پرسش به‌جای حدود ۲ میلی‌ثانیه حدود ۹۰ میلی‌ثانیه طول می‌کشد و صفحه‌ها چند ثانیه کند می‌شوند. منطقهٔ پروژهٔ موجود را در `Project Settings` ← `General` ← `Region` و در نشانی اتصال (`aws-…-eu-central-1.pooler…`) ببینید (قدم ۲-۷).

   - منطقه را بعداً نمی‌توان عوض کرد. اگر پیام `Selected region is at capacity` آمد، یک منطقهٔ دیگر اروپا را بزنید.
5. `Postgres version`: پیش‌فرض را دست نزنید. گزینهٔ `OrioleDB` را انتخاب نکنید.
6. بخش امنیت (`Security`):
   - تیک `Enable Data API` را **بردارید**. برنامه از این رابط استفاده نمی‌کند و خاموش بودنش امن‌تر است. پیام `Client libraries need Data API to query your database` طبیعی است.
   - `Enable automatic RLS` را هر طور بود بگذارید؛ فایل schema خودش RLS را روشن می‌کند.
7. `Create new project` را بزنید و چند دقیقه صبر کنید.

**باید ببینید:** صفحهٔ پروژه بدون پیام `Setting up project`، و نشان سبز سلامت پروژه.

### ۱-۴. رشتهٔ اتصال (Transaction pooler)

1. بالای صفحهٔ پروژه دکمهٔ `Connect` را بزنید.
2. زبانهٔ `Direct` (یا `Connection String`) را باز کنید.
3. `Type`: `URI`.
4. `Connection Method` (یا `Method`): **`Transaction pooler`**. نه `Direct connection` و نه `Session pooler`.
5. نشانی را کپی کنید. شکلش این است:
   ```
   postgresql://postgres.abcdefghijklmnop:[YOUR-PASSWORD]@aws-1-eu-central-1.pooler.supabase.com:6543/postgres
   ```
6. عبارت `[YOUR-PASSWORD]` را **همراه با کروشه‌ها** پاک کنید و رمز قدم ۱-۳ را جایش بگذارید:
   ```
   postgresql://postgres.abcdefghijklmnop:Xk3pQ9vT2mL7wRb4@aws-1-eu-central-1.pooler.supabase.com:6543/postgres
   ```
7. این نشانی کامل را در مدیر رمز ذخیره کنید. در Vercel نامش `DATABASE_URL` است.

چند نکته که بیشترین خطاها از آن‌هاست:

- **نام کاربری** باید `postgres.` و بعد شناسهٔ پروژه باشد (مثل `postgres.abcdefghijklmnop`)، نه فقط `postgres`.
- **میزبان** (`aws-0-…` یا `aws-1-…`) را دستی ننویسید؛ همان را که کپی کرده‌اید نگه دارید.
- **پورت** باید `6543` باشد.
- چیزی مثل `?pgbouncer=true` به انتها اضافه نکنید (برنامه خودش prepared statement را خاموش می‌کند).
- `Direct connection` (نشانی `db.<شناسه>.supabase.co:5432`) در پلن رایگان فقط IPv6 دارد و Vercel به IPv6 وصل نمی‌شود.
- اگر رمز نویسهٔ خاص دارد، آن را در نشانی به این شکل بنویسید (یا ساده‌تر: رمز را با `Generate a password` عوض کنید، قدم ۱۰-۳):

| نویسه | `@` | `#` | `/` | `:` | `%` | `+` | `?` | `&` | `=` | فاصله |
|---|---|---|---|---|---|---|---|---|---|---|
| در نشانی | `%40` | `%23` | `%2F` | `%3A` | `%25` | `%2B` | `%3F` | `%26` | `%3D` | `%20` |

**باید ببینید:** نشانی‌ای که با `postgresql://postgres.` شروع می‌شود، `[` و `]` ندارد، به `:6543/postgres` ختم می‌شود و رمز واقعی داخل آن است.

### ۱-۵. ساختن پایگاه داده (معمولاً لازم نیست)

ساختن جدول‌ها (۵۳۰ جدول در ۸۴ مرحله) **کار خود برنامه است** و یکی از این سه راه به‌ترتیب انجامش می‌دهد. هر مرحله در تراکنش خودش اجرا و ثبت می‌شود؛ پس هر راهی که نیمه‌کاره بماند، راه بعدی دقیقاً از همان‌جا ادامه می‌دهد و هیچ مرحله‌ای دو بار انجام نمی‌شود.

1. **ساخت Vercel (پیش‌فرض، کاری لازم نیست):** وقتی `DATABASE_URL` را گذاشتید و Redeploy کردید (قدم ۲-۵)، ساخت پیش از انتشار همهٔ مرحله‌ها را اجرا می‌کند. در `Deployments` ← انتشار ← `Building` سطرهای `[migrate-db]` را می‌بینید و آخرش `done: 84/84 steps`. اگر ساخت به پایگاه داده نرسید، فقط هشدار می‌دهد و انتشار ادامه می‌یابد (راه ۳).
2. **یک دستور از هر رایانه (برای اطمینان یا پیش از اولین انتشار):** Node.js 22 به بالا لازم است. در پوشهٔ `itsm` مخزن یک بار `npm ci` و بعد:
   ```bash
   DATABASE_URL='نشانی قدم ۱-۴' npx tsx scripts/migrate-db.mts
   ```
   در PowerShell ویندوز: `$env:DATABASE_URL='نشانی قدم ۱-۴'; npx tsx scripts/migrate-db.mts`. خروجی پیشرفت هر مرحله را نشان می‌دهد و با `done: 84/84 steps` تمام می‌شود. اجرای دوباره بی‌خطر است؛ `--status` فقط می‌گوید پایگاه داده کجاست.
3. **خود برنامه:** اگر پایگاه داده هنوز کامل نیست، اولین بازدیدکننده صفحهٔ «آماده‌سازی پایگاه داده» را با درصد پیشرفت می‌بیند. صفحه هر چند ثانیه خودش می‌پرسد و هر پرسش، چند مرحله را در حداکثر ۲۵ ثانیه پیش می‌برد (تا مهلت ۶۰ ثانیه‌ای Vercel نرسد). روی پلن رایگان Supabase کل کار حدود یک تا دو دقیقه است. پس از آن صفحهٔ ورود باز می‌شود.

**اجرای دستی در SQL Editor (فقط اگر بخواهید):** SQL Editor در Supabase کوئری بزرگ‌تر از حدود ۱ مگابایت را نمی‌پذیرد (`Query is too large to be run via the SQL Editor`)، پس فایل یک‌جای [`supabase/schema.sql`](../supabase/schema.sql) (حدود ۲٫۷ مگابایت) آن‌جا اجرا نمی‌شود. به‌جایش همان مرحله‌ها در **۹ بخش** حداکثر ۴۰۰ کیلوبایتی آمده‌اند: [`supabase/manual`](../supabase/manual) ← `01-of-09.sql` تا `09-of-09.sql`.

1. در GitHub به `itsm/supabase/manual/01-of-09.sql` در شاخهٔ `main` بروید و `Copy raw file` (نماد دو مربع) را بزنید.
2. Supabase ← `SQL Editor` ← `+` ← `Create a new snippet`، متن را بچسبانید و `Run` (یا `Ctrl+Enter`). خط اولش باید بگوید «بخش ۱ از ۹».
3. اگر پنجرهٔ `Potential issues detected` باز شد و از `destructive operations` یا `tables without enabling Row Level Security` گفت: **هر دو هشدار نادرست است.** «حذف» فقط `drop trigger if exists` پیش از ساخت دوباره است، و RLS در انتهای هر مرحله برای همهٔ جدول‌ها روشن می‌شود. `Run and enable RLS` را بزنید (`Run without RLS` هم درست است).
4. `Success. No rows returned` را ببینید و همین کار را با `02-of-09.sql` تا `09-of-09.sql` **به‌ترتیب** تکرار کنید (برای هر بخش یک snippet تازه، یا متن قبلی را پاک کنید).

هر بخش در تراکنش خودش اجرا می‌شود؛ اگر بخشی خطا بدهد، همان بخش ثبت نمی‌شود و بخش‌های قبلی سر جایشان می‌مانند. متن خطا را نگه دارید و بقیه را به برنامه بسپارید (راه ۳).

**بررسی** (هر کدام از راه‌ها): نشانی `https://نشانی-شما/api/health` (پس از انتشار، قدم ۲-۵)، یا این کوئری در SQL Editor:

```sql
select
  (select count(*) from pg_tables
     where schemaname = 'public' and tablename like 'sm\_%')                     as tables,
  (select count(*) from pg_tables
     where schemaname = 'public' and tablename like 'sm\_%' and not rowsecurity) as tables_without_rls,
  (select count(*) from sm_migrations)                                          as migrations,
  (select max(id) from sm_migrations)                                           as last_migration;
```

**باید ببینید:** یک ردیف با `tables` = `530`، `tables_without_rls` = `0`، `migrations` = `24` و `last_migration` = `0099_demo_touch`. با نسخه‌های بعدی عددها بزرگ‌تر می‌شوند؛ آنچه همیشه باید صفر باشد `tables_without_rls` است.

### ۱-۶. بررسی هشدارهای امنیتی (Advisors)

1. منوی کناری ← `Advisors` ← `Security Advisor`.

**باید ببینید:** فقط این موارد، که همه طبیعی‌اند:
- `RLS Enabled No Policy` (سطح `INFO`، برای جدول‌های `sm_…`): عمداً هیچ قانون دسترسی تعریف نشده تا کلیدهای عمومی به هیچ داده‌ای نرسند. برنامه با کاربر `postgres` (مالک جدول‌ها) وصل می‌شود و RLS جلویش را نمی‌گیرد.
- `Function Search Path Mutable` (سطح `WARN`، برای `sm_sync_touch`، `sm_user_touch` و `sm_audit_actor`): این‌ها تابع‌های داخلی trigger هستند و از بیرون صدا زده نمی‌شوند.

هشداری با سطح `ERROR` (مثل `Table publicly accessible`) نباید باشد. اگر بود، فهرست بررسی امنیت (بخش ۱۱) را مرور کنید.

### ۱-۷. خاموش کردن Data API (اگر در قدم ۱-۳ روشن ماند)

1. منوی کناری ← `Integrations` ← `Data API` (یا `Project Settings` ← `Data API`).
2. کلید `Enable Data API` را خاموش کنید و ذخیره کنید.

با این کار نشانی REST پروژه به هیچ درخواستی پاسخ نمی‌دهد. `Table Editor` و `SQL Editor` مثل قبل کار می‌کنند. فایل schema هم همهٔ دسترسی‌های `anon` و `authenticated` را از جدول‌های `sm_…` گرفته است؛ این کار لایهٔ دوم حفاظت است.

**باید ببینید:** کلید `Enable Data API` خاموش.

> **SSL:** برنامه همیشه با اتصال رمزنگاری‌شده وصل می‌شود. اگر بخواهید، در `Database` ← `Settings` ← `SSL Configuration` گزینهٔ `Enforce SSL on incoming connections` را روشن کنید (پایگاه داده چند ثانیه راه‌اندازی دوباره می‌شود). برنامه در هر دو حالت کار می‌کند.

## ۲. انتشار روی Vercel

### ۲-۱. حساب Vercel

1. [vercel.com/signup](https://vercel.com/signup) را باز کنید.
2. نوع حساب: `Hobby`.
3. `Continue with GitHub` و ورود با **همان حساب GitHub که مالک مخزن `ai` است**.

اگر برای پروژه‌های دیگر همین مخزن از قبل حساب Vercel دارید، با همان وارد شوید.

**باید ببینید:** داشبورد Vercel با فهرست پروژه‌ها.

### ۲-۲. ساخت پروژهٔ تازه و Import مخزن

1. مستقیم [vercel.com/new](https://vercel.com/new) را باز کنید (دکمهٔ داشبورد گاهی `Add New…` ← `Project` و گاهی `Create New` ← `Project` نام دارد).
2. در بخش `Import Git Repository` کنار مخزن `ai` دکمهٔ `Import` را بزنید.
   - اگر `ai` در فهرست نیست: `Configure GitHub App` (یا در GitHub: `Settings` ← `Applications` ← `Installed GitHub Apps` ← `Vercel` ← `Configure`) ← `Repository access` ← `All repositories`، یا `Only select repositories` و افزودن `ai` ← `Save`. بعد به vercel.com/new برگردید.

این یک **پروژهٔ تازه و جدا** است. به پروژه‌های موجود مخزن دست نزنید.

**باید ببینید:** صفحهٔ `Configure Project` (یا `New Project`) با نام مخزن `ai`.

### ۲-۳. تنظیم پروژه

1. `Project Name`: بنویسید `itsm`.
2. `Root Directory`: دکمهٔ `Edit` ← پوشهٔ **`itsm`** را انتخاب کنید ← `Continue`. **مهم‌ترین قدم همین است.** اگر روی ریشهٔ مخزن بماند، Vercel به‌جای ITSM برنامهٔ دیگری را می‌سازد.
3. `Framework Preset`: باید خودش `Next.js` شود. اگر `Other` بود، `Next.js` را انتخاب کنید.
4. `Build and Output Settings`: دست نزنید. دستور ساخت از `itsm/vercel.json` خوانده می‌شود (`npm run build`: ساخت رابط کاربری با Vite و بعد Next.js برای API). نسخهٔ Node هم از `engines` در `itsm/package.json` (Node 22) خوانده می‌شود.
5. `Environment Variables`: فعلاً خالی بگذارید. در قدم ۲-۵ آن‌ها را فقط برای `Production` اضافه می‌کنیم.
6. `Deploy` را بزنید.

**باید ببینید:** گزارش `Building` و پس از چند دقیقه صفحهٔ موفقیت (`Congratulations` و دکمهٔ `Continue to Dashboard`).

### ۲-۴. آزمون اول: ساخت درست است

1. `Continue to Dashboard` را بزنید. زیر `Domains` نشانی پروژه را می‌بینید، مثلاً `itsm-xyz.vercel.app`. این **نشانی اصلی** است؛ نشانی‌های طولانی که شناسهٔ هر انتشار را دارند (مثل `itsm-abc123-….vercel.app`) را به کسی ندهید.
2. این نشانی را باز کنید: `https://itsm-xyz.vercel.app/api/health`

**باید ببینید:** پاسخی با `"code":"not_configured"` و پیام «پایگاه داده تنظیم نشده است: متغیر DATABASE_URL را در Vercel بگذارید…». یعنی برنامه درست ساخته شده و فقط پایگاه داده را کم دارد. اگر `404: NOT_FOUND` دیدید، `Root Directory` یا `Framework Preset` اشتباه است (جدول رفع اشکال).

### ۲-۵. متغیرهای محیطی

1. پروژه ← `Settings` ← `Environment Variables`.
2. برای هر ردیف جدول زیر: `Key` را بنویسید، `Value` را بچسبانید، در `Environments` فقط **`Production`** را تیک بزنید، برای ردیف‌هایی که «محرمانه»اند نوع `Secret` (در نسخه‌های قدیمی‌تر: تیک `Sensitive`) را انتخاب کنید، و `Save`.
3. پس از افزودن همه: `Deployments` ← روی آخرین انتشار دکمهٔ `⋯` ← `Redeploy` ← دوباره `Redeploy`. متغیرها فقط در انتشار تازه اثر دارند.

**ساخت مقدارهای تصادفی:** در ترمینال (یا Git Bash روی ویندوز) `openssl rand -hex 32` را اجرا کنید. اگر ترمینال ندارید، در مدیر رمز یک رمز ۶۴ نویسه‌ای از حرف و عدد بسازید. مقدار `Secret` در Vercel دیگر قابل دیدن نیست؛ **نسخه‌ای از آن را خودتان نگه دارید.**

| نام | لازم؟ | نمونهٔ مقدار | نوع | اگر نباشد |
|---|---|---|---|---|
| `DATABASE_URL` | **لازم** | `postgresql://postgres.abcd…:رمز@aws-1-eu-central-1.pooler.supabase.com:6543/postgres` (قدم ۱-۴) | Secret | همهٔ درخواست‌های `/api` پاسخ ۵۰۳ «پایگاه داده تنظیم نشده است» می‌دهند و کسی وارد نمی‌شود. برنامه به‌جای آن `SUPABASE_DB_URL` یا `POSTGRES_URL` را هم می‌پذیرد. |
| `APP_SECRET` | **عملاً لازم** | خروجی `openssl rand -hex 32` (۶۴ نویسه) | Secret | کلیدهای هوش مصنوعی ذخیره نمی‌شوند. کلید وب‌هوک‌ها با کلیدی ساخته‌شده از `DATABASE_URL` رمزنگاری می‌شود و با تعویض رمز پایگاه داده از دست می‌رود. «سلامت سامانه» هشدار «کلید رمزنگاری» می‌دهد. **پس از گذاشتن هرگز عوضش نکنید**؛ وگرنه کلیدها و رمزهای ذخیره‌شده خوانده نمی‌شوند و باید دوباره وارد شوند. |
| `PLATFORM_ADMIN_EMAILS` | **پیشنهادی** | `you@example.com` (چند ایمیل با `,` انگلیسی) | Config | اولین حسابی که در سایت ساخته شود، هر کسی باشد، مدیر کل سامانه می‌شود. با این متغیر فقط حسابی با همین ایمیل مدیر کل می‌شود، آن هم تا وقتی سامانه هیچ مدیر فعالی ندارد. |
| `CRON_SECRET` | پیشنهادی | خروجی `openssl rand -hex 16` | Secret | هر کسی می‌تواند نشانی بیدار نگه داشتن Supabase را صدا بزند. این نشانی فقط `select 1` اجرا می‌کند و خطری ندارد، ولی بهتر است بسته باشد. |
| `ALLOW_SIGNUP` | اختیاری | `false` | Config | پیش‌فرض باز است: هر کسی حساب می‌سازد و سازمان خودش را تعریف می‌کند. با `false` فقط شما (و مدیران هر سازمان از «تنظیمات ← کاربران و دسترسی‌ها») حساب می‌سازید. |
| `PUBLIC_URL` | اختیاری | `https://itsm.example.ir` | Config | فقط به‌عنوان نشانی معرفی برنامه به سرویس هوش مصنوعی OpenRouter فرستاده می‌شود. بدون آن فقط نام برنامه فرستاده می‌شود. |
| `AUTO_MIGRATE` | اختیاری | `false` | Config | پیش‌فرض `true`: ساخت Vercel، و اگر نشد خود برنامه، مرحله‌های پایگاه داده را اجرا می‌کند (قدم ۱-۵). با `false` هیچ‌کدام کاری نمی‌کنند و تا `scripts/migrate-db.mts` یا بخش‌های `supabase/manual` را اجرا نکنید، سایت «پایگاه داده به‌روز نیست» می‌گوید. |
| `MIGRATE_STEP_BUDGET_MS` | اختیاری | `25000` | Config | زمانی که هر درخواست پس از پاسخ، صرف مرحله‌های پایگاه داده می‌کند (فقط وقتی پایگاه داده کامل نیست). پیش‌فرض ۲۵ ثانیه در مهلت ۶۰ ثانیه‌ای Vercel؛ دست نزنید. |
| `MIGRATE_ON_PREVIEW` | اختیاری | `true` | Config | ساخت‌های `Preview` هرگز پایگاه داده را تغییر نمی‌دهند، حتی اگر `DATABASE_URL` داشته باشند. فقط برای پایگاه دادهٔ جداگانهٔ Preview آن را `true` کنید. |
| `DATABASE_POOL_MAX` | اختیاری | `3` | Config | پیش‌فرض ۳ اتصال هم‌زمان برای هر نمونهٔ سرور. برای پلن رایگان Supabase کافی است؛ بیشترش نکنید. |
| `DATABASE_SSL` | اختیاری | `disable` | Config | پیش‌فرض: اتصال رمزنگاری‌شده. `disable` فقط برای PostgreSQL شخصی بدون SSL است. **برای Supabase هرگز نگذارید.** |

> `ITSM_AI_FAKE` فقط برای آزمون خودکار است و `ITSM_DATA_DIR`، `ITSM_STATIC_DIR`، `ITSM_PORT`، `ITSM_SMOKE`، `ITSM_SMOKE_OUT` و `ITSM_UI_OUT` فقط برای نسخهٔ ویندوز و ساخت آن‌اند. هیچ‌کدام را در Vercel نگذارید. نمونهٔ همهٔ متغیرهای وب در [`itsm/.env.example`](../.env.example) است.

**چرا فقط `Production`؟** با هر push به هر شاخه، Vercel یک انتشار `Preview` می‌سازد. اگر `DATABASE_URL` در Preview هم باشد، کد آزمایشی یک شاخه می‌تواند تغییرات پایگاه دادهٔ خودش را روی پایگاه دادهٔ اصلی اعمال کند. بدون این متغیر، Preview فقط پیام «پایگاه داده تنظیم نشده است» می‌دهد و آسیبی نمی‌زند. برای آزمودن Preview، یک پروژهٔ Supabase دوم بسازید و نشانی آن را فقط برای `Preview` بگذارید.

**باید ببینید:** در گزارش ساخت (`Deployments` ← انتشار ← `Building`) سطرهای `[migrate-db]` و آخرش `done: 84/84 steps` (یا `up to date`). پس از انتشار، نشانی `https://itsm-xyz.vercel.app/api/health` این را نشان می‌دهد:
```json
{"ok":true,"db":"ok","mode":"cloud","version":"1.1.0","schema":{"complete":true,"done":80,"total":80,"percent":100,"next":null},"pooler":"transaction"}
```
- `db`: `ok` یعنی پایگاه داده پاسخ می‌دهد؛ وگرنه متن خطای اتصال (جدول بخش ۹).
- `schema`: مرحلهٔ `done` از `total`. تا کامل نشده، پاسخ ۵۰۳ با `"code":"migrating"` و درصد پیشرفت است و سایت صفحهٔ «آماده‌سازی پایگاه داده» را نشان می‌دهد.
- `pooler`: باید `transaction` باشد (نشانی پورت `6543`). `session` یا `direct` یعنی نشانی اشتباه گذاشته‌اید (قدم ۱-۴).

### ۲-۶. حداکثر زمان اجرا (فقط بررسی)

کاری لازم نیست. درخواست‌های عادی تا ۶۰ ثانیه و پاسخ‌های دستیار هوش مصنوعی تا ۳۰۰ ثانیه (بیشترین مقدار پلن Hobby) فرصت دارند. این تنظیم در خود کد است (`app/api/[[...route]]/route.ts` و `app/api/o/[org]/ai/[[...route]]/route.ts`). `Settings` ← `Functions` ← `Fluid Compute` باید روشن باشد (پیش‌فرض پروژه‌های تازه).

### ۲-۷. منطقهٔ اجرای سرور: فرانکفورت (فقط بررسی، ولی حتماً)

> **سرور Vercel (`fra1`) و پایگاه دادهٔ Supabase (`eu-central-1`) باید هر دو در فرانکفورت باشند.** این مهم‌ترین عامل سرعت نسخهٔ وب است: یک صفحه ده‌ها پرسش به پایگاه داده می‌فرستد و فاصلهٔ دو قاره هر پرسش را حدود ۴۵ برابر کند می‌کند.

پروژه‌های تازهٔ Vercel سرور را در واشنگتن (`iad1`) اجرا می‌کنند. این تنظیم در خود کد است (`itsm/vercel.json` ← `"regions": ["fra1"]`) و کاری لازم نیست؛ فقط بررسی کنید.

1. پروژه ← `Settings` ← `Functions` ← بخش `Function Regions`.

**باید ببینید:** `Frankfurt, Germany (fra1)` انتخاب‌شده (با یادداشتی که می‌گوید این تنظیم از `vercel.json` می‌آید). برای اطمینان بیشتر: نشانی `/api/health` را باز کنید، با `F12` بخش `Network` را باز و صفحه را تازه کنید و روی درخواست `health` بزنید؛ در `Response Headers` سرآیند `x-vercel-id` عبارت `fra1` را دارد.

اگر پروژهٔ Supabase را در منطقهٔ دیگری ساخته‌اید، مقدار `regions` در `itsm/vercel.json` را به نزدیک‌ترین منطقهٔ Vercel به آن تغییر دهید (فهرست: [vercel.com/docs/regions](https://vercel.com/docs/regions)).

### ۲-۸. چند پروژهٔ Vercel روی یک مخزن (Ignored Build Step)

هر پروژهٔ Vercel که به این مخزن وصل است با هر push ساخته می‌شود و پلن Hobby هم‌زمان فقط یک ساخت انجام می‌دهد. برای این‌که ITSM فقط با تغییر پوشهٔ خودش ساخته شود:

1. پروژهٔ `itsm` ← `Settings` ← `Build and Deployment` (در راهنماهای قدیمی‌تر: `Git`) ← `Ignored Build Step`.
2. `Behavior`: `Custom`.
3. `Command`:
   ```bash
   git diff --quiet "${VERCEL_GIT_PREVIOUS_SHA:-HEAD^}" HEAD -- .
   ```
4. `Save`.

این دستور تغییرات از آخرین انتشار موفق تا الان را در پوشهٔ `itsm` (همان `Root Directory`) بررسی می‌کند. در پروژه‌ای که ریشهٔ مخزن را می‌سازد هم پوشهٔ `itsm` را کنار بگذارید، مثلاً:

```bash
git diff --quiet "${VERCEL_GIT_PREVIOUS_SHA:-HEAD^}" HEAD -- . ':(exclude)itsm'
```

**باید ببینید:** در push بعدی که فقط پوشهٔ دیگری را تغییر داده، انتشار `itsm` در `Deployments` با وضعیت `Canceled` (ساخت لازم نبود) دیده می‌شود.

### ۲-۹. حفاظت انتشارها (Deployment Protection)

`Settings` ← `Deployment Protection` ← `Vercel Authentication` روی `Standard Protection` بماند (پیش‌فرض). با آن، نشانی‌های Preview و نشانی‌های طولانی هر انتشار فقط با ورود به Vercel باز می‌شوند. **نشانی اصلی و دامنهٔ اختصاصی عمومی می‌مانند.**

نتیجه: به نسخهٔ ویندوز و گوشی همیشه نشانی اصلی (`itsm-xyz.vercel.app`) یا دامنهٔ اختصاصی را بدهید. نشانی محافظت‌شده به‌جای پاسخ برنامه، صفحهٔ ورود Vercel برمی‌گرداند و اتصال ناموفق می‌شود.

## ۳. اولین حساب و کنسول مدیریت سامانه

1. نشانی اصلی سایت را باز کنید.
2. صفحهٔ «ورود به کاریز» ← پیوند ساخت حساب. اگر ثبت‌نام بسته است و پیوند دیده نمی‌شود، نشانی `/signup` را مستقیم باز کنید.
3. در «ساخت حساب کاریز» نام، **همان ایمیل `PLATFORM_ADMIN_EMAILS`** و رمزی دست‌کم ۸ نویسه (نه فقط عدد) بنویسید و حساب را بسازید.
4. **کد بازیابی** نمایش داده می‌شود. آن را در مدیر رمز ذخیره کنید (یا «ذخیره در فایل»). بدون ایمیل، این تنها راه بازیابی رمز است.
5. سازمان را با ویزارد بسازید: «نام سازمان» (مثلاً «واحد فناوری اطلاعات شرکت نمونه») و «منطقهٔ زمانی» (پیش‌فرض تهران) ← «ساخت سازمان» ← «رفتن به خانه».
6. از منوی حساب «مدیریت سامانه» را بزنید، یا نشانی `/admin` را باز کنید.
7. بخش «سلامت سامانه» را باز کنید.

**باید ببینید:** در «سلامت سامانه»: «پایگاه داده» «در دسترس»، «ساختار پایگاه داده» «به‌روز (۴ مرحله)»، «کلید رمزنگاری» «APP_SECRET تنظیم شده است» و «مدیران سامانه» «۱ ایمیل در PLATFORM_ADMIN_EMAILS». هر مورد زرد یا قرمز توضیح و راه رفع خودش را دارد.

> این قدم را **بلافاصله پس از انتشار** انجام دهید. اگر `PLATFORM_ADMIN_EMAILS` را خالی گذاشته باشید، هر کس زودتر از شما حساب بسازد مدیر کل سامانه می‌شود.

بعد همکاران را اضافه کنید: داخل سازمان ← «تنظیمات» ← «کاربران و دسترسی‌ها» ← ایمیل، نام و نقش. برای حساب تازه رمز موقت نمایش داده می‌شود. مدیران دیگر سامانه را از خود کنسول اضافه کنید: «کاربران» ← کاربر ← «مدیریت سامانه». جزئیات در بخش ۸.

## ۴. بیدار ماندن Supabase (Cron)

پروژهٔ رایگان Supabase اگر یک هفته کم‌کار بماند، متوقف (`Paused`) می‌شود. `itsm/vercel.json` هر روز یک بار نشانی `/api/cron/keepalive` را صدا می‌زند تا پایگاه داده بیدار بماند. کار دیگری لازم نیست؛ فقط بررسی کنید:

1. پروژهٔ Vercel ← `Settings` ← `Cron Jobs`.

**باید ببینید:** ردیف `/api/cron/keepalive` با زمان `41 3 * * *`. در پلن Hobby این کار هر روز در یک لحظهٔ دلخواه بین ساعت ۰۳:۰۰ و ۰۳:۵۹ به وقت جهانی (حدود ۶:۳۰ تا ۷:۳۰ صبح تهران) اجرا می‌شود. فردا با `View Logs` باید درخواستی با وضعیت `200` ببینید.

آزمون دستی (با `CRON_SECRET` خودتان):
```bash
curl -H "Authorization: Bearer CRON_SECRET_شما" https://itsm-xyz.vercel.app/api/cron/keepalive
# پاسخ درست: {"ok":true}
```

اگر پروژه با این حال متوقف شد: داشبورد Supabase ← پروژه ← `Resume project` ← تأیید. چند دقیقه بعد برنامه دوباره کار می‌کند. پروژهٔ متوقف را زیاد معطل نگذارید؛ Supabase پس از مدتی امکان بازگرداندن را برمی‌دارد.

### ۴-۱. صف کارهای پس‌زمینه (هر دقیقه؛ پیشنهادی)

کارهای پس‌زمینه (اعلان‌ها، زمان‌سنج‌های توافق سطح خدمت، یادآوری‌ها…) در صفی در پایگاه داده می‌مانند. نسخهٔ وب پس از هر تغییری که کاری در صف بگذارد، همان کار را بلافاصله پس از پاسخ انجام می‌دهد و `itsm/vercel.json` هم روزی یک بار نشانی `/api/cron/tick` را صدا می‌زند؛ ولی کارهای زمان‌دار (مثلاً هشدار نزدیک شدن موعد) به ضربانی هر دقیقه نیاز دارند. Vercel در پلن Hobby فقط روزی یک بار اجرا می‌کند، پس این ضربان را خود Supabase بزند:

1. داشبورد Supabase ← پروژه ← `Database` ← `Extensions`: دو افزونهٔ `pg_cron` و `pg_net` را روشن کنید.
2. `SQL Editor` ← `New query`، نشانی برنامه و `CRON_SECRET` خودتان را بگذارید و `Run` بزنید:

```sql
select cron.schedule('itsm-tick', '* * * * *', $$
  select net.http_post(
    url := 'https://itsm-xyz.vercel.app/api/cron/tick',
    headers := jsonb_build_object('Authorization', 'Bearer CRON_SECRET_شما')
  );
$$);
```

**باید ببینید:** در `Integrations` ← `Cron` ردیف `itsm-tick`؛ چند دقیقه بعد در `History` اجراهای موفق. آزمون دستی:
```bash
curl -X POST -H "Authorization: Bearer CRON_SECRET_شما" https://itsm-xyz.vercel.app/api/cron/tick
# پاسخ درست: {"ok":true,"ran":0,"failed":0,"more":false}
```
برای برداشتن: `select cron.unschedule('itsm-tick');`. نسخهٔ ویندوز به این کار نیازی ندارد؛ صف خودش را هر ۱۰ ثانیه اجرا می‌کند.

## ۵. دامنهٔ اختصاصی و دسترسی از داخل ایران

دامنه‌های `vercel.app` گاهی در ایران محدود می‌شوند. با دامنهٔ اختصاصی وضعیت بهتر است و نشانی هم برای کاربران ثابت می‌ماند.

### ۵-۱. افزودن دامنه

1. پروژهٔ Vercel ← `Settings` ← `Domains` ← `Add Domain`.
2. دامنه را بنویسید، مثلاً `itsm.example.ir`، و آن را به `Production` وصل کنید.
3. Vercel رکورد DNS لازم را نشان می‌دهد:
   - برای زیردامنه (مثل `itsm.example.ir`): یک رکورد `CNAME` با مقداری که **همان صفحه** نشان می‌دهد. مقدار عمومی قدیمی را از جای دیگری کپی نکنید.
   - برای دامنهٔ اصلی بدون زیردامنه: رکورد `A` با نشانی‌ای که همان صفحه نشان می‌دهد.
   - اگر دامنه قبلاً در حساب Vercel دیگری بوده، یک رکورد `TXT` روی `_vercel` هم خواسته می‌شود.
4. این رکورد را در پنل DNS دامنه بسازید (ثبت‌کنندهٔ دامنه، DNS ابرآروان یا Cloudflare). لازم نیست NS دامنه را به Vercel منتقل کنید.
5. چند دقیقه تا چند ساعت صبر کنید.
6. متغیر `PUBLIC_URL` را به `https://itsm.example.ir` تغییر دهید و Redeploy کنید (اختیاری).

**باید ببینید:** کنار دامنه در `Domains` عبارت `Valid Configuration`، و `https://itsm.example.ir/api/health` همان پاسخ `"ok":true` را می‌دهد. گواهی SSL را Vercel خودکار می‌سازد.

### ۵-۲. CDN یا سرور داخلی (اختیاری)

- برای پایداری بیشتر می‌توانید یک CDN داخلی (مثل ابرآروان) جلوی دامنه بگذارید. سه شرط دارد:
  1. CDN باید سرآیند `Host` را همان دامنهٔ شما نگه دارد و به `….vercel.app` تغییرش ندهد. وگرنه ورود و هر ذخیره‌ای خطای ۴۰۳ «درخواست از مبدأ نامعتبر» می‌دهد.
  2. حالت SSL باید `Full (strict)` باشد. حالت `Flexible` حلقهٔ بی‌پایان تغییر مسیر می‌سازد.
  3. مسیرهای `/.well-known/acme-challenge/*` و `/.well-known/vercel/*` بی‌چالش و بی‌کش به Vercel برسند و `index.html` کش نشود.
- بعضی کاربران ایرانی گاهی از Vercel خطای ۴۰۳ می‌گیرند، چون پشت نشانی‌های اینترنت مشترک کشور هستند. اگر این مشکل جدی شد، برنامه را روی یک سرور داخلی اجرا کنید (همان کد Next.js به‌شکل `standalone` ساخته می‌شود):
  ```bash
  cd itsm && npm ci && npm run build
  DATABASE_URL=... APP_SECRET=... node .next/standalone/server.js   # پوشه‌های public و .next/static را کنار آن کپی کنید
  ```
  روی سرور داخلی، cron ندارید؛ یک زمان‌بند روزانه نشانی `/api/cron/keepalive` را صدا بزند.
- برای یک دفتر کوچک بدون اینترنت پایدار، نسخهٔ ویندوز با «حالت شبکه» خودش سرور داخلی است ([DESKTOP_FA.md](DESKTOP_FA.md)).

## ۶. گوشی و نسخهٔ ویندوز

دادهٔ اصلی همهٔ سازمان‌ها در Supabase است. نسخهٔ وب هر صفحه را مستقیم از آن می‌خواند، پس هر رایانه یا گوشی که وارد شود همان داده را می‌بیند. نسخهٔ ویندوز یک نسخهٔ کامل از دادهٔ سازمان را روی رایانه نگه می‌دارد تا بی‌اینترنت هم کار کند و با Supabase هم‌گام می‌ماند. هر عضو با **همان ایمیل و رمز** در وب، گوشی و ویندوز وارد می‌شود. توضیح کامل: [ARCHITECTURE_FA.md](ARCHITECTURE_FA.md) و [DESKTOP_FA.md](DESKTOP_FA.md).

### ۶-۱. گوشی

نشانی اصلی یا دامنهٔ اختصاصی را در مرورگر گوشی باز کنید و وارد شوید. برای داشتن نشان برنامه روی صفحهٔ اصلی: در Chrome اندروید منوی `⋮` ← `Install app` یا `Add to Home screen`، و در Safari آیفون `Share` ← `Add to Home Screen`.

**باید ببینید:** همان سازمان‌ها و همان داده‌های رایانه، و تغییری که در دستگاه دیگری ثبت شود پس از چند ثانیه روی صفحهٔ باز گوشی.

### ۶-۲. نسخهٔ ویندوز (فایل نصب)

**دریافت:** صفحهٔ `Releases` مخزن در GitHub ← آخرین «کاریز (Kariz) … نسخهٔ ویندوز» (برچسب `itsm-vX.Y.Z`؛ پیش‌نمایش شاخه‌های دیگر: `itsm-preview-<شاخه>`) ← فایل `Kariz-Setup-x.y.z.exe`. GitHub Actions این فایل را با هر push در پوشهٔ `itsm` روی یک ویندوز واقعی می‌سازد، بی‌صدا نصب و آزمایش می‌کند و منتشر می‌کند (`.github/workflows/itsm.yml`). همان فایل در `Actions` ← اجرای آخر ← `Artifacts` ← `itsm-windows-installer` هم هست.

**نصب:** فایل را روی هر رایانهٔ ویندوز ۱۰ یا ۱۱ (۶۴ بیتی) اجرا کنید ← «بعدی» ← «موافقم» ← محل نصب ← «نصب». همه‌چیز (برنامه، پایگاه دادهٔ داخلی، قلم‌ها) در همین یک فایل است و به اینترنت یا نصب چیز دیگری نیاز ندارد.

> **هشدار SmartScreen:** چون فایل نصب امضای دیجیتال تجاری ندارد، ویندوز ممکن است `Windows protected your PC` نشان دهد ← `More info` ← `Run anyway`. برای حذف این پیام باید یک گواهی Code Signing بخرید و در GitHub Secrets (`CSC_LINK` و `CSC_KEY_PASSWORD`) بگذارید.

**وصل کردن به نسخهٔ وب:**
- اگر در وب سازمان دارید: در اولین اجرا «اتصال به حساب ابری» ← نشانی سایت (نشانی اصلی یا دامنهٔ اختصاصی، نه نشانی Preview)، ایمیل و رمز ← انتخاب سازمان. همهٔ اطلاعات دریافت می‌شود.
- اگر روی ویندوز شروع کرده‌اید: «تنظیمات ← نسخهٔ ویندوز ← هم‌گامی با نسخهٔ وب» ← «اتصال به حساب ابری» ← بارگذاری سازمان همین رایانه. سازمان در وب ساخته می‌شود و از آن به بعد هم‌گام می‌ماند.

**باید ببینید:** نشانک بالای صفحه «هم‌گام». تغییری که در ویندوز ثبت کنید چند ثانیه بعد در وب دیده می‌شود. بی‌اینترنت، تغییرها در صف می‌مانند («… در صف») و با وصل شدن فرستاده می‌شوند.

## ۷. هوش مصنوعی

هر سازمان کلید سرویس دلخواهش یا مدل محلی را در «تنظیمات ← هوش مصنوعی» وصل می‌کند (هر کسی که سطح «کامل» هوش مصنوعی دارد: مالک و مدیر). پیش از آن، `APP_SECRET` باید در Vercel باشد (قدم ۲-۵)؛ وگرنه کلید ذخیره نمی‌شود. کلیدها رمزنگاری‌شده ذخیره می‌شوند و هرگز به مرورگر برنمی‌گردند. مدیر کل سامانه می‌تواند هوش مصنوعی هر سازمان یا کل سامانه را از کنسول خاموش کند. راهنمای کامل، همراه با گرفتن کلید رایگان Gemini، پشتیبان‌های رایگان و مدل‌های محلی: [AI_FA.md](AI_FA.md).

## ۸. مدیریت سامانه و سطح‌های دسترسی

- **مدیر کل سامانه** (`PLATFORM_ADMIN_EMAILS`): کنسول `/admin` با «پیشخوان»، «سازمان‌ها» (وضعیت فعال / فقط‌خواندنی / معلق، یادداشت داخلی، خاموش کردن هوش مصنوعی)، «کاربران» (غیرفعال کردن، خروج از همهٔ دستگاه‌ها، رمز موقت با ذکر دلیل، دادن یا گرفتن مدیریت سامانه)، «هوش مصنوعی» (سیاست و مصرف هر سازمان، هرگز کلید)، «رویدادهای امنیتی» و «سلامت سامانه».
- ایمیل `PLATFORM_ADMIN_EMAILS` فقط تا وقتی سامانه هیچ مدیر فعالی ندارد دسترسی مدیر می‌دهد (حتی اگر ثبت‌نام بسته باشد). اگر حساب این ایمیل مدیر سامانه باشد، مدیر دیگری نمی‌تواند غیرفعالش کند یا دسترسی‌اش را بگیرد. حسابی با این ایمیل که مدیر نیست (کسی که پس از شما با آن ثبت‌نام کرده) در کنسول با برچسب نشانی مالک سامانه بدون دسترسی مدیر دیده می‌شود و می‌توان غیرفعالش کرد. برای هیچ مدیر سامانه‌ای (و تا ۷ روز پس از گرفتن دسترسی‌اش) رمز موقت گذاشته نمی‌شود.
- مدیر کل سامانه دادهٔ سازمانی را که عضوش نیست مستقیم نمی‌بیند. برای پشتیبانی، از صفحهٔ همان سازمان «حالت پشتیبانی» را با ذکر دلیل، سطح («فقط مشاهده» یا «مشاهده و اصلاح») و حداکثر ۴ ساعت شروع می‌کند. هر کار در این حالت با برچسب پشتیبانی در «گزارش رویدادها»ی همان سازمان ثبت می‌شود و مالک می‌تواند جلسه را زودتر تمام کند. حتی در سطح اصلاح، پشتیبانی کلید API، وب‌هوک یا اتصال هوش مصنوعی نمی‌سازد و اعضا را تغییر نمی‌دهد.
- **داخل هر سازمان** (مدل دسترسی موقت تا ساخت ماژول‌های ITSM): **مالک** (همه‌چیز)، **مدیر** (مثل مالک، جز تغییر مالکان)، **عضو** (دیدن سازمان، اعضا و گزارش‌ها، پرسش از دستیار و آماده کردن پیش‌نویس؛ بدون تغییر تنظیمات) و **ناظر** (فقط مشاهده و پرسش از دستیار). دسترسی هر عضو را می‌توان در پنج بخش («تنظیمات سازمان»، «کاربران و دسترسی‌ها»، «اتصال‌ها و API»، «هوش مصنوعی و دستیار»، «گزارش‌ها») و چهار سطح (بدون دسترسی، مشاهده، ثبت و ویرایش، کامل) جداگانه تغییر داد.
- هیچ‌کس جز مالک نقش یا دسترسی خودش را تغییر نمی‌دهد و کسی نمی‌تواند به دیگری دسترسی بیشتر از خودش بدهد. رمز عضو را فقط وقتی می‌توان از «کاربران و دسترسی‌ها» عوض کرد که حسابش در همین سازمان ساخته شده باشد؛ وگرنه خودش از «حساب کاربری من» یا با کد بازیابی عوض می‌کند.

## ۹. رفع اشکال

پیش از هر چیز `https://نشانی-شما/api/health` را باز کنید (قدم ۲-۵): `db` خطای اتصال پایگاه داده را دقیق می‌گوید، `schema` می‌گوید چند مرحله از پایگاه داده انجام شده (`done` از `total`) و `version` نسخهٔ برنامه است. هر «خطای داخلی سرور» یک **کد پیگیری** هشت‌نویسه‌ای دارد (مثلاً `کد پیگیری: 3f9a1c2e`)؛ همان را در `Logs` جست‌وجو کنید تا متن کامل خطا را ببینید. گزارش سرور در Vercel ← پروژه ← `Logs` است (فیلتر `Level: Error`). در پلن Hobby این گزارش فقط **یک ساعت** نگه داشته می‌شود؛ مشکل را تکرار کنید و فوراً نگاه کنید.

### ۹-۱. نسخهٔ وب خطای سرور می‌دهد، یا «قبلاً ثبت شده» و بعد خطا در ورود

**چه اتفاقی افتاده بود:** نسخه‌های قبلی ساختن همهٔ جدول‌ها (حدود ۲٫۵ مگابایت دستور) را در اولین درخواست و در یک قدم انجام می‌دادند. روی Vercel این قدم به مهلت ۶۰ ثانیه نمی‌رسید یا قطع می‌شد؛ برنامه خطا را فقط در `Logs` می‌نوشت و با پایگاه دادهٔ نیمه‌کاره (فقط ۵ مرحلهٔ اول) کار می‌کرد. ثبت‌نام اول، حساب را می‌ساخت ولی ساختن نشست ورود روی ستونی که هنوز نبود شکست می‌خورد («خطای سرور»)؛ ثبت‌نام دوباره «قبلاً ثبت شده» می‌گفت و ورود هم به همان دلیل خطا می‌داد. حساب نسخهٔ ویندوز در این ماجرا نقشی نداشت: حساب‌های ویندوز هرگز خودشان به سرور نمی‌روند.

**این نسخه:** هیچ درخواستی روی پایگاه دادهٔ نیمه‌کاره پاسخ داده نمی‌شود، مرحله‌ها کوچک و قابل ادامه‌اند و ثبت‌نام یک تراکنش است (یا همه‌اش انجام می‌شود یا هیچ‌چیز). برای پایگاه دادهٔ فعلی شما **هیچ SQL دستی لازم نیست**:

1. این نسخه را منتشر کنید (`main` ← Vercel خودش می‌سازد). اگر `DATABASE_URL` در Vercel هست، ساخت همان‌جا مرحله‌های جاافتاده را اجرا می‌کند؛ در گزارش ساخت `[migrate-db] … done: 84/84 steps` را ببینید.
2. `https://نشانی-شما/api/health` را باز کنید. **باید ببینید:** `"ok":true` و `"schema":{"complete":true,…}`. اگر هنوز ۵۰۳ و `migrating` است، سایت را باز کنید و صفحهٔ «آماده‌سازی پایگاه داده» را تا آخر باز نگه دارید (یا راه ۲ قدم ۱-۵ را اجرا کنید).
3. به صفحهٔ **ورود** بروید (نه ثبت‌نام) و با همان ایمیل مدیر و **همان رمزی که در اولین تلاش ثبت‌نام نوشتید** وارد شوید. حساب سالم است و چون ایمیلش در `PLATFORM_ADMIN_EMAILS` است، مدیر کل سامانه است. پس از ورود، ویزارد ساخت سازمان باز می‌شود (بخش ۳ قدم ۵).
4. اگر آن رمز را به یاد ندارید: کد بازیابی آن ثبت‌نام هرگز نمایش داده نشده بود، پس حساب نیمه‌کاره را پاک کنید و دوباره ثبت‌نام کنید. Supabase ← `SQL Editor`، ایمیل خودتان را به‌جای `you@example.com` بگذارید و `Run`:
   ```sql
   delete from sm_users u
    where lower(u.email) = lower('you@example.com')
      and not exists (select 1 from sm_org_members m where m.user_id = u.id);
   ```
   **باید ببینید:** `Success. 1 rows affected` (اگر `0 rows` بود، حساب عضو سازمانی است و پاک نمی‌شود؛ با رمزش وارد شوید). حالا در سایت `/signup` را باز کنید، با همان ایمیل ثبت‌نام کنید و **کد بازیابی** را نگه دارید.
5. اگر در `/api/health` مقدار `schema.error` آمد یا درصد جلو نمی‌رود: از هر رایانه‌ای `DATABASE_URL='نشانی' npx tsx scripts/migrate-db.mts` را اجرا کنید (قدم ۱-۵، راه ۲). خروجی، مرحلهٔ مشکل‌دار و متن کامل خطا را نشان می‌دهد.

**شروع پایگاه داده از صفر** (همهٔ داده‌ها پاک می‌شود؛ فقط وقتی هنوز داده‌ای ندارید):

1. Supabase ← `SQL Editor`، این را بچسبانید و `Run` بزنید. هر اجرا ۱۰۰ جدول از جدول‌های برنامه (`sm_…`) را پاک می‌کند، نه چیزی از خود Supabase (یک‌جا پاک کردن همه با خطای `out of shared memory` روبه‌رو می‌شود):
   ```sql
   do $$
   declare r record; n int := 0;
   begin
     for r in select tablename from pg_tables where schemaname = 'public' and tablename like 'sm\_%'
                and tablename not in ('sm_orgs', 'sm_users') order by tablename limit 100 loop
       execute format('drop table if exists %I cascade', r.tablename);
       n := n + 1;
     end loop;
     if n = 0 then
       drop table if exists sm_orgs cascade;
       drop table if exists sm_users cascade;
       for r in select p.oid::regprocedure as f from pg_proc p join pg_namespace n on n.oid = p.pronamespace
                 where n.nspname = 'public' and p.proname like 'sm\_%' loop
         execute format('drop function if exists %s cascade', r.f);
       end loop;
     end if;
   end $$;
   select count(*) as tables_left from pg_tables where schemaname = 'public' and tablename like 'sm\_%';
   ```
   همان را آن‌قدر دوباره `Run` بزنید تا `tables_left` = `0` شود (حدود ۷ بار).
2. یکی از راه‌های قدم ۱-۵ را بروید (ساده‌ترین: در Vercel ← `Deployments` ← `⋯` ← `Redeploy`).
3. `/api/health` ← `"ok":true`، بعد بخش ۳ (اولین حساب).

راه دیگر: پروژهٔ Supabase تازه‌ای بسازید (بخش ۱)، `DATABASE_URL` را در Vercel عوض و Redeploy کنید.

## ۱۰. به‌روزرسانی، پشتیبان‌گیری و تعویض رمز

### ۱۰-۱. به‌روزرسانی برنامه

1. تغییرات را در GitHub به `main` ادغام کنید. Vercel خودش انتشار `Production` تازه می‌سازد.
2. پروژه ← `Deployments`: آخرین انتشار باید `Ready` شود.
3. مرحله‌های تازهٔ پایگاه داده در همان ساخت اجرا می‌شوند (سطرهای `[migrate-db]` در گزارش ساخت)؛ نسخهٔ قبلی تا پایان ساخت بی‌مشکل کار می‌کند، چون تغییرات پایگاه داده فقط چیز اضافه می‌کنند. اگر ساخت به پایگاه داده نرسید، اولین بازدیدکننده‌ها چند لحظه صفحهٔ «آماده‌سازی پایگاه داده» را می‌بینند.

**باید ببینید:** `/api/health` ← `"ok":true` و `"schema":{"complete":true,…}` با `version` نسخهٔ تازه.

- **برگرداندن نسخهٔ قبلی:** `Deployments` ← انتشار قبلی ← `⋯` ← `Instant Rollback`. فقط کد برمی‌گردد، نه پایگاه داده؛ مشکلی نیست چون تغییرات پایگاه داده فقط چیز اضافه می‌کنند.
- **اگر `AUTO_MIGRATE=false` گذاشته‌اید:** پیش از ادغام `scripts/migrate-db.mts` را با کد تازه اجرا کنید، یا بخش‌های [`itsm/supabase/manual`](../supabase/manual) را به‌ترتیب در SQL Editor (اجرای دوبارهٔ بخش‌هایی که قبلاً اجرا شده بی‌خطر است).
- **نسخهٔ ویندوز:** فایل نصب تازه را از `Releases` روی نسخهٔ قبلی نصب کنید؛ داده‌ها می‌مانند. همیشه اول نسخهٔ وب را به‌روز کنید، بعد ویندوز را ([DESKTOP_FA.md](DESKTOP_FA.md)).

### ۱۰-۲. پشتیبان‌گیری

پلن رایگان Supabase پشتیبان خودکار ندارد. یکی از این دو راه را حتماً داشته باشید:

- **نسخهٔ ویندوز متصل:** روی یک رایانه نسخهٔ ویندوز را به سازمان وصل نگه دارید. هر ۶ ساعت از کل داده‌ها پشتیبان می‌گیرد (۳۰ نسخهٔ آخر).
- **`pg_dump` هفتگی:** در `Connect` نشانی **`Session pooler`** (پورت `5432`) را بردارید و اجرا کنید:
  ```bash
  pg_dump "postgresql://postgres.شناسه:رمز@aws-1-eu-central-1.pooler.supabase.com:5432/postgres" \
    --schema=public --format=custom --file=itsm-1405-08-16.dump
  ```
  نسخهٔ `pg_dump` باید هم‌نسخه یا تازه‌تر از Postgres پروژه باشد (`Database` ← `Settings`). فایل را جای امنی بیرون از رایانهٔ اصلی نگه دارید.

پلن Pro (ماهانه ۲۵ دلار) پشتیبان روزانهٔ ۷ روزه دارد و هرگز متوقف نمی‌شود.

### ۱۰-۳. تعویض رمز پایگاه داده

اگر رمز لو رفت یا نویسهٔ خاص داشت:

1. پیش از هر چیز مطمئن شوید `APP_SECRET` در Vercel هست. بدون آن، کلید رمزنگاری از `DATABASE_URL` ساخته می‌شود و با تعویض رمز، کلید وب‌هوک‌های ذخیره‌شده از دست می‌رود.
2. Supabase ← `Database` ← `Settings` ← `Reset database password` ← `Generate a password` ← رمز را ذخیره کنید ← `Reset password`.
3. Vercel ← `Settings` ← `Environment Variables` ← `DATABASE_URL` ← `Edit` ← نشانی با رمز تازه ← `Save`.
4. **فوراً** `Deployments` ← `⋯` ← `Redeploy`، و چند دقیقه صبر کنید.

**باید ببینید:** پیام `Successfully updated database password` در Supabase و پس از Redeploy، `/api/health` با `"db":"ok"`. نسخهٔ ویندوز اثری نمی‌بیند، چون با نسخهٔ وب حرف می‌زند نه مستقیم با پایگاه داده.

## ۱۱. فهرست بررسی امنیت

پیش از دادن نشانی به دیگران، این‌ها را تیک بزنید:

- [ ] `APP_SECRET` گذاشته شده و نسخه‌ای از آن بیرون از Vercel نگه داشته شده است.
- [ ] `DATABASE_URL`، `APP_SECRET` و `CRON_SECRET` از نوع `Secret` و فقط برای `Production` هستند.
- [ ] `PLATFORM_ADMIN_EMAILS` ایمیل خودتان است و اولین حساب را خودتان ساخته‌اید؛ در «سلامت سامانه» «مدیران سامانه» سبز است.
- [ ] کد بازیابی حساب مدیر در مدیر رمز ذخیره شده است.
- [ ] اگر سامانه عمومی نیست، `ALLOW_SIGNUP=false` است.
- [ ] `Enable Data API` در Supabase خاموش است و `Security Advisor` هیچ مورد `ERROR` ندارد.
- [ ] نتیجهٔ کوئری بررسی قدم ۱-۵ برای `tables_without_rls` صفر است.
- [ ] `Deployment Protection` روی `Standard Protection` است.
- [ ] تأیید دومرحله‌ای (2FA) برای حساب‌های GitHub، Vercel و Supabase روشن است.
- [ ] رمز پایگاه داده جز در مدیر رمز و Vercel جایی نیست (نه در پیام‌رسان، نه در مخزن).
- [ ] پشتیبان‌گیری (نسخهٔ ویندوز متصل یا `pg_dump` هفتگی) برقرار است.
- [ ] نسخهٔ ویندوز و گوشی‌ها با نشانی اصلی یا دامنهٔ اختصاصی وصل شده‌اند.

اطلاعات امنیتی برنامه: رمزها با scrypt هش می‌شوند؛ نشست‌ها توکن تصادفی‌اند و فقط هش آن‌ها ذخیره می‌شود؛ «خروج از همهٔ دستگاه‌ها» در «حساب کاربری من» است؛ کلیدهای هوش مصنوعی و کلید وب‌هوک‌ها با `APP_SECRET` رمزنگاری می‌شوند و از کلید API فقط هش ذخیره می‌شود؛ همهٔ تغییرات سازمان در «گزارش رویدادها» و کارهای امنیتی در «رویدادهای امنیتی» کنسول ثبت می‌شوند.

## ۱۲. توسعهٔ محلی

```bash
cd itsm
npm ci
npm run build:ui                      # رابط کاربری در public/
npm run start:local                   # نسخهٔ «ویندوزی» بدون Electron روی http://127.0.0.1:3939 (پایگاه داده در .local-data)
DATABASE_URL=postgres://… npm run dev # نسخهٔ وب (Next.js) — npm run dev:ui برای رابط کاربری با Vite
npm run typecheck && npm test && npm run check:schema && npm run build
npm run schema                        # پس از تغییر migrationها: supabase/schema.sql را به‌روز می‌کند
node scripts/ui-shots.mjs             # عکس همهٔ صفحه‌ها (روشن، تیره، گوشی) با گزارش خطا
npm run qa:crawl                      # بررسی کلیک‌به‌کلیک همهٔ صفحه‌ها با سه نقش؛ گزارش در docs/qa/CLICKTHROUGH.md
```

«بررسی کلیک‌به‌کلیک» (`scripts/ui-crawl.mjs`) برنامه را همان‌طور که روی ویندوز اجرا می‌شود بالا می‌آورد (کارساز محلی روی
PGlite با سازمان نمونه)، با فرم ورود به‌عنوان مدیر سامانه، کارشناس پشتیبانی و درخواست‌دهنده وارد می‌شود و همهٔ مسیرهای ثبت‌شده
در رابط کاربری را باز می‌کند: روی فهرست‌ها «… تازه» را می‌زند و نخستین رکورد را با همهٔ زبانه‌ها باز می‌کند، روی صفحه‌های دیگر
دکمهٔ اصلی سربرگ، نخستین نوار یا کارت و نخستین پیوند را. خطای کنسول، خطای اجرا، صفحهٔ «پیدا نشد»، فراخوانی ناموفق API،
بارگذاری بی‌پایان (بیش از ۱۵ ثانیه) و اسکرول افقی در عرض گوشی (۳۹۰) را گزارش می‌کند. اجرای کامل حدود ۳۵ دقیقه طول می‌کشد؛
`--quick` (صفحه‌های اصلی هر بخش، بدون رکوردها؛ حدود ۷ دقیقه) در CI اجرا می‌شود و `--only <الگو>` بخشی از مسیرها را بررسی می‌کند (`--merge` نتیجه را
در گزارش قبلی می‌نشاند). گزینه‌ها در سرآغاز همان فایل آمده‌اند.

ساخت فایل نصب ویندوز روی رایانهٔ خودتان (روی ویندوز؛ روی لینوکس به Wine نیاز دارد):

```bash
cd itsm && npm ci && (cd desktop && npm ci)
node scripts/build-desktop.mjs
cd desktop && npx electron-builder --win nsis --x64
```
