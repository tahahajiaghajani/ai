# ITSM (provisional name) — notes for Claude

Fully independent project in a sub-folder of this repository (own package.json and lockfile, Vercel project with Root Directory `itsm`, own Supabase project, own Windows installer). A Persian (RTL) enterprise IT service management application with AI, running as a **web app** (Vercel + Supabase) and a **Windows app** (Electron + embedded PostgreSQL/PGlite) kept in sync. This version is the platform foundation only — accounts, organisations, members and roles, AI, integrations, the platform owner's console, desktop ↔ cloud sync, the Windows app and CI; the ITSM modules come later. Read `docs/ARCHITECTURE_FA.md`, `docs/SETUP_FA.md`, `docs/DESKTOP_FA.md`, `docs/AI_FA.md` and `src/ui/ds/README.md` before larger changes.

- **Name.** The product's name is provisional. Use `APP_NAME`, `APP_NAME_EN`, `APP_TAGLINE`, `APP_TAGLINE_EN`, `APP_DESCRIPTION` from `src/shared/constants.ts`; never hard-code it (index.html and manifest.webmanifest are filled by `vite.config.ts`, the splash gets it in its query string, NSIS uses `${PRODUCT_NAME}`; `desktop/electron-builder.yml` repeats `APP_NAME_EN` and `tests/desktop.test.ts` checks it). Internal identifiers never derive from the name and stay when it changes: tables `sm_*`, PostgreSQL settings `itsm.*`, environment variables `ITSM_*`, IPC channels `itsm:*`, `window.itsm`, storage keys `itsm.*`, appId `app.itsm.desktop`, data dir `%APPDATA%\ITSM`. The mark is a placeholder monogram (`src/ui/components/brand.tsx`, rasterised into every icon by `desktop/scripts/make-icons.cjs`).
- **One codebase, two runtimes.** UI: `src/ui` (React 19, Ant Design 6 RTL, Tailwind 4; the design system in `src/ui/ds` — read its README before touching UI: `--ds-*` tokens only, no raw hex, Dusk used sparingly, type in Arad with every digit from «DS Num» and weights only from `--ds-weight-*`, tabular numbers that never ellipsize, `lucide-react` icons, Vite → `public/`). API: one Hono app (`src/server/app.ts`) mounted by Next.js on Vercel (`src/server/cloud.ts`, postgres.js) and by the desktop local server (`src/desktop/server.ts`, PGlite). Shared logic in `src/shared` (exact numbers with decimal.js — never floats for stored values; Jalali dates; validators; entity definitions; permissions; AI contracts).
- **Database:** tables `sm_*`, RLS on with no policies. Migrations are TS modules in `src/server/db/migrations` (idempotent SQL: `if not exists`, `create or replace`, `drop … if exists`; never edit a shipped one, add a new file and register it in `index.ts`), applied automatically on both runtimes; `npm run schema` regenerates `supabase/schema.sql` + `supabase/migrations/*.sql` (CI checks with `npm run check:schema`, `tests/schema.test.ts` runs every migration twice).
- **Sync:** engine tables sync automatically (pushes judged by the access provider and the engine's values, pulls filtered with tombstones, `bumpScopeEpoch` when what a member may read changes). Other aggregate roots carry `rev/updated_at/deleted_at/origin`; trigger `sm_sync_touch('<entity>')` stamps the writing transaction's id as the revision (cloud; no lock, any commit order — pulls compare snapshots, `src/server/sync/snapshot.ts`) or queues `sm_outbox` (desktop, `itsm.mode = 'desktop'`; nothing is queued while `itsm.applying = 'on'`). New synced roots need the trigger in a migration and an entry in `src/server/sync/registry.ts` (`tests/sync-registry.test.ts` checks both; deliberately local tables are listed there). Changing children must update the root row. Soft-delete roots. Numbered records keep `no` with a unique index named `*_no_*` (engine numbers from the row-locked `sm_numbers` counter); codes use an index whose name contains the column. Bump `SYNC_PROTOCOL` when a synced table gains a column or a new synced kind appears.
- **Record engine** (read `docs/spec/ENGINE.md` before touching records): every ITSM table — incidents, CIs, KB, and configuration like SLA definitions — is a `TableDef` in `src/shared/tables/<module>.ts` (listed in `MODULE_TABLES`); the engine generates its DDL (no migration for new tables/fields: `reconcileSchema`; run `npm run schema` after changing a TableDef), sync root, validation, history, events and the generic API `/api/o/:org/r/:table…` + `/meta/tables`. Server code uses `@server/engine` (`list/get/create/update/transition/remove/aggregate`, inside a transaction `createIn/updateIn/transitionIn/removeIn`, `systemCtx` for jobs) — never raw SQL writes to engine tables. Behaviour goes into `registerHooks(table, { beforeWrite, afterWrite, validateTransition, guards })` (same transaction, no model or network calls), reactions into `onRecordEvent(name, fn)` and background work into the job queue (`enqueue` inside the write's tx, `registerJobHandler`). Filters are conditions (`@shared/model/conditions`: one JSON language, `evaluate` ↔ `toSql` parity); every read path of your own starts from `readable(ctx, def, alias, params, env)` and strips fields with `visibleFields` — all security goes through the access provider (`src/server/access/provider.ts`). Concurrency token is `version` (not `rev`); `number` for people, `id` for machines.
- **Record UI** (read `docs/spec/UI_RECORDS.md` before building a module's screens): `src/ui/records` renders any engine table — `RecordList` (views, filters, columns, bulk, inline edit, board/calendar/timeline), `RecordPage` (header, form with UI policies, conflicts, side panel, activity stream and composer), `FieldInput`/`FieldValue`, `FilterBuilder`. A module registers its tables with `recordModule()` (`records/module.tsx`) and adds behaviour through `registerRecordExtensions` (presets, header/side-panel/tab widgets, composer slots `cannedResponses`/`aiDraft`, UI policies); every table also works at `r/:table`. Pure logic lives in `records/model` (tests `tests/ui-records-*.test.ts`).
- **SLA service** (read `docs/spec/services/sla.md` before touching record writes): `src/server/modules/sla` (`installSlaService()` in `routes/modules.ts`) and `src/ui/modules/sla` own working calendars and holidays (business-time arithmetic in `@shared/sla/calendar`), SLA timers (`meta.sla`, `sla_due`, `record.sla_warning`/`record.sla_breach` once by job), approvals (a table's `approval` field, participant read access, «تأییدهای من», delegation) and the rules of records (priority matrix, categories, business and assignment rules, UI policies also enforced on the server and on sync pushes) — hooks on `"*"` in a fixed order. Modules plug in with `registerPriorityDefault`, `registerApproverSource`, `setOnCallResolver`.
- **Flows** (no-code automation; read `docs/spec/services/flows.md` before touching it): flows, versions, HTTP connections and schedules are engine tables (`src/shared/tables/flows.ts`, area `flows`); runs, step logs, waits and timers are runtime tables of the executing runtime (`sm_flow_*`, never synced). The executor (`src/server/modules/flows`) persists every step (record steps inside their write transaction), resumes waits through jobs and guards steps per run and the depth of flows started by flows. Other services plug in with `registerFlowStepHandler` (the notification and SLA services replace the `notify` and `approval` stand-ins and set the business clock — `src/server/modules/{notify,sla}/flows.ts`, index `docs/spec/SERVICES.md`; `builtinStepHandler` keeps the stand-ins for tests and record-less approvals), `registerFlowSkill`, `setFlowBusinessClock`, `resumeFlowWait`, `startCatalogFlows`; the shared model (`src/shared/flows`: node catalogue, data pills, Jalali schedules, validator) serves the designer (`src/ui/modules/flows`, @xyflow/react + dagre) and the server alike.
- **Writes** only inside `ctx.write(async (tx) => …)` using `tx` (PGlite is single-connection; the organisation's platform status — read-only, suspended — is enforced there; writes of one organisation run side by side: a value derived from several rows is recomputed in `onBeforeCommit` work, which takes a lock per key, or under a lock of the row it decides). Check permissions with `ctx.need(area, level)` on the server and `can()` in the UI. Record security-relevant actions with `securityEvent()` and organisation changes with `audit()`.
- **Access model (provisional):** AREAS `settings`, `users`, `integrations`, `ai`, `reports`, `work` (generic records: «کار», saved views); roles owner, admin («مدیر», the owner's deputy), member, viewer, with per-area overrides (`src/shared/permissions.ts`, one rule `memberChangeRule` for the members API, pushed member rows and the members page). A platform admin (`is_platform_admin`) who is not a member has NO access except through an audited support session (`src/server/modules/platform`, `context.ts`). `tests/permissions.test.ts` checks every area named on the server, in the sync registry and in the UI. A new ITSM access model replaces this later.
- **ITSM access model** (read `docs/spec/ACCESS.md` before touching access; admin guide `docs/ACCESS_FA.md`): installed as the engine's provider everywhere (`src/server/access`, `installAccessModel()` in `routes/modules.ts`). Org structure, groups, workspaces, member profiles and roles are engine tables (`src/shared/tables/access.ts`); roles grant read/create/write/delete/approve/admin per area (`@shared/access`: `registerArea` for a module's area) with scopes none < own < group < unit < unit_tree < domain < all; built-in roles live in code (an org row replaces one). Declare a table's scope columns in `TableDef.scope` (own, requester, group, watchers, requesterWritable, requesterTransitions, confidentialGroup, public) and field groups on fields. The SQL form (`readSql`) and the JS form (`canReadRow`/`writeMode`) must stay equal (`tests/access-parity.test.ts`). Notifications use `readersOf`/`memberCtx`, retrieval `readableIds`; never read engine tables around the provider. `scope.readers` are user fields that read and never write (the request module's `fulfillers`: a task's assignee from another group reads the item and its order, never changes them). Participant sources (`registerParticipantSource`) declare `reach` — `scoped` adds rows, `grant` reads the rows it names without an area grant (the approver grant: whoever has or had an approval on a record reads it) — and `bounded` for roles in context the record does not name (the service owners: never past a secure workspace or restricted group); a grant participant reaches only single-record reads, the record page shows them the extensions with `participants: true` (approvals, «هوش مصنوعی»). Members without ITSM roles keep their membership role's access («حالت پیشین»); the membership role still governs the platform's own pages (`ctx.can`).
- **UI conventions:** every page starts with `PageHeader`; use the kit in `src/ui/components/*` (`ServerTable`, `EntityPage`, `NumberInput`, `DateInput` (Jalali), `RefSelect`, `JDate`, `StatusTag`, `Card`, `Note`, `EmptyState`); all text Persian; Persian digits via `faDigits`/`formatNumber`; logical spacing utilities; AntD v6 props (`Drawer size`, `destroyOnHidden`, `Alert title`, `Tag variant`). Explanations live in «راهنما» (`src/ui/modules/settings/Help.tsx`), not on the pages.
- **Modules** register nav groups, spaces, routes and palette searches in `src/ui/modules/<module>/index.tsx` (assembled in `src/ui/modules/registry.tsx`), API routes in `src/server/routes/<module>.ts` (mounted in `src/server/routes/modules.ts`), master data in `ENTITIES` (`src/shared/entities.ts`, generic CRUD and spreadsheet import), synced aggregates with `registerAggregate`, AI tools with `registerTool` and proposal executors with `registerProposalExecutor`, webhook topics with `registerTopicHandler`, live query keys with `registerLiveQueries`, assistant starters in `src/ui/ai/assistant/prompts.ts` and page context in `context.ts`. `tests/fixtures/module.ts` is a stand-in module registered exactly this way; tests of the generic machinery use it.
- **Desktop:** Electron main/preload/splash in `desktop/src` (`main.ts` sets `%APPDATA%\ITSM` explicitly, runs the local server in a utility process, `--smoke-test` with `ITSM_SMOKE`/`ITSM_SMOKE_OUT`/`ITSM_DATA_DIR`; `preload.ts` exposes only `window.itsm` and `itsm:*` IPC; `splash.html` is the 520×320 frameless splash driven through `itsm.step/progress/status/version/ready`), Windows art in `desktop/build` (`cd desktop && npm run icons`), packaging `desktop/electron-builder.yml` (NSIS, Persian, `ITSM-Setup-x.y.z.exe`, installs to `%LOCALAPPDATA%\Programs\ITSM\ITSM.exe`), build `node scripts/build-desktop.mjs` then `cd desktop && npx electron-builder --win`. CI `.github/workflows/itsm.yml` (repository root) builds on Windows, smoke-tests and publishes to Releases (`itsm-vX.Y.Z` from `main`, `itsm-preview-<branch>` otherwise; the server MSI is added only to its own commit's release).
- **AI** (docs/AI_FA.md): per-organisation connections and keys (encrypted, never returned) in `src/server/modules/ai`; Claude only through `@anthropic-ai/sdk` 1.x (no temperature/top_p/top_k, adaptive thinking, no forced tool_choice, replay native content unchanged, append-only history); never call a model inside `ctx.write`/`db.tx`. Assistant tools (`modules/ai/tools`) must repeat their route's permission and module checks, return bounded data with units and Jalali periods, and never write — writes are proposals confirmed by a person (`tools/proposals.ts`). Numbers come from code (`analytics`), the model only narrates. AI tables are LOCAL_ONLY (each runtime has its own keys). Shared contracts: `src/shared/ai/{types,api}.ts`. Test mode: `ITSM_AI_FAKE=1`.
- **Tools, agents and the virtual agent** (read `docs/spec/AI.md` §11.8–11.9): every readable table gets generated tools (`modules/ai/tools/records.ts`: search/get/aggregate/history, drafts as proposals applied with the applier's access; a new table is covered as it is, `excludeFromTools` keeps one out), picked per turn by tool retrieval (`tools/select.ts`); module tools over services in `tools/modules.ts`. Agents (`modules/ai/agents`, tables `ai_agent`/`ai_agent_run` in `src/shared/tables/ai-agents.ts`) act only through a service member of their own whose roles an owner chooses (`skills/principal.ts` with the agent's key), run as resumable `ai.agent.run` jobs, propose (routed to the record's group or the agent's approvers, `route_only`) or apply whitelisted low-risk actions (`applyByAgent`), with guardrails checked on what would be written, budgets and kill switches (`features.agents`); `registerAgent` adds a module's. The virtual agent (`modules/ai/va`, `/ai/va/*`, `VirtualAgentAdapter` in `src/shared/ai/va.ts`) works with the requester's context throughout; the portal builds its UI. Tests: `tests/ai-agents-*.test.ts`, `tests/ai-tools-*.test.ts`.
- **Retrieval (RAG) and smart documents** (read `docs/spec/AI.md`): `src/server/modules/ai/rag` (`installRag()` in `routes/modules.ts`) indexes every table that declares `ai: { title, text }` / `features.rag` (or a builder registered with `registerRagSource`, which may add an AI-channel rule `aiWhere`) into local tables `sm_ai_chunks`/`sm_ai_rag_docs` — one partition per field group, never `ai_private`/secrets — with full text, the deterministic local embedder and the organisation's embedding model (`embed` on connections); pgvector on Supabase and PGlite, float arrays otherwise. `retrieve(ctx, …)` and `askWithCitations(ctx, …)` run only with the asking member's ctx, join every chunk to its source row through `readable(...)` in the same SQL, re-check the hits, and cite only readable records; `<AskPanel scope>` (`src/ui/ai/ask`) is the UI. «اسناد هوشمند»: engine tables `doc_collection`/`doc_document` (area knowledge, sharing by row rule), uploads read by `docs.ingest`. Leak tests: `tests/ai-rag-leak.test.ts`.
- **Notifications** (read `docs/spec/services/notify.md`): rules, templates, messaging channels and e-mail channels are engine tables (built-in rules live in code; a row with `builtin` replaces one); every message is rendered per recipient under that recipient's access (`memberCtx`: no access → nothing, hidden fields «(محدود)»), delivered by jobs (`notify.send`/`notify.hook`/`notify.flush`, inbound mail `notify.imap`) and logged in `sm_notification_log`. Services raise `record.<event>` events (people in `data.users`/`data.approvers`) or call `notifyPeople()` — never SMTP, messengers or SMS gateways directly. The bell and notification center are in the top bar (`src/ui/modules/notify`).
- **Predictive AI, «پرسش تحلیلی», insights and AI governance** (read `docs/spec/AI.md` §12–16): classical models in TypeScript, trained per organisation on each runtime (`modules/ai/ml`: registry `sm_ai_models` generated from the metadata, predictions `sm_ai_predictions` shown only to readers of the record and only for fields they see, a model used only when it beats its baseline, jobs `ai.ml.*`; more targets with `registerPredictionTarget`, probability models with `registerRiskModel`; assignment rules take the predicted group above `threshold_apply` through `setAssignmentPredictor`). `askReport` (`modules/ai/nlreport.ts`) checks a model's report definition against the metadata and the asker's access and computes numbers with `runReport`, never a model. Insights (`modules/ai/insights`) are computed as the system and shown to a member only when they read every record a card was computed from (live count check); digests are built per recipient. The per-table data-use policy (`ai_data_policy`, `modules/ai/datause.ts`: cloud / local only / never) is enforced in `runTurn`: every model call that carries record data names its tables (`tables` of generate/runTurn, `dataTables` of skills; the assistant and agents from their tool results). Governance console `/ai/governance/*` (ai:full). Tests `tests/ai-ml-*.test.ts`, `tests/ai-insights-*.test.ts`.
- **Incident and problem management** (the first ITSM modules and the pattern for the others; guides `docs/modules/incident_FA.md`, `problem_FA.md`): tables `src/shared/tables/{incident,problem}.ts` (task tables with their own state models, scope, form, related lists, `ai` documents; choice lists registered on a line of their own in `tables/index.ts`), pure logic `src/shared/{incident,problem}/logic.ts` and API contracts `src/shared/incident/api.ts`, server `src/server/modules/{incident,problem}` (`install*Module()` in `routes/modules.ts` after the SLA service — one incident hook sits on `"*"` to see the matrix's priority; hooks for data, `onRecordEvent` subscribers gated by `actsHere` for reactions, a self-rescheduling per-organisation sweep job, idempotent seeds with a `seeded` marker on the module's settings row, record meta telling the UI what the caller may do, routes answering with `get()`-shaped records), routes `src/server/routes/{incident,problem}.ts`, UI `src/ui/modules/{incident,problem}` (space «عملیات», queues as list pages with fixed filters, header actions, side panels, the war room, the RCA canvas), tests `tests/incident-*.test.ts`, `tests/problem-*.test.ts` (`tests/incident-helpers.ts` builds an organisation with every built-in role). Outage banners: `announcement` rows reach people through `GET /incident/announcements` (audience-filtered; the table itself is the owning group's). Requester-only creators file incidents without the desk's fields (`INCIDENT_REQUESTER_FIELDS`); child rows (tasks, reviews) need someone who works the parent. Extension points: `createFromAlert` (event module), `record.incident.major_declared` (continuity), `registerIncidentAi`/`registerProblemAi` (AI layer).
- **Change enablement** (`docs/modules/change_FA.md`): tables `src/shared/tables/change.ts` (one state model for every change model; a change snapshots its model's lifecycle in `model_states`), pure logic `src/shared/change/logic.ts` (lifecycles, requirements and locks, risk engine, Jalali window recurrences, conflicts, slots, scores — shared with the screens), server `src/server/modules/change` (`installChangeModule()` after the SLA service: hooks and the lifecycle guard, the authorization cycle on the approvals service with approver sources `change_manager`/`cab`/`ecab`/`service_owner`, conflicts planned before the write and stored after it, CAB, PIR, lockdowns, jobs and the sweep, seed), routes `src/server/routes/change.ts` (`/change/*`), screens `src/ui/modules/change` (space «تغییر»: queues, change calendar, CAB workbench, standard catalogue, dashboard). Extension points: `registerImpactProvider` (CMDB), `registerChangeAi` (AI layer), POST `/change/detected` (discovery). With incident management: «ثبت تغییر» on incidents, problems, known errors and requested items (a confidential source makes a confidential change), suspects from the incident's CIs, services and `detected_at`, `incidents_caused` counting `caused_by` links from incidents only (`countsAsIncident`). Bookkeeping fields the module stamps (alert stamps, CAB votes and decisions, conflict copies, lockdown counters) are `system`: user input, rules and flows never set them, the module's trusted writes do (`{ trusted: true }`). The change manager's authority (`managesChanges`: the change area's approve right through the change_manager or tenant_admin role) guards manual authorization (never by the change's own people), the definitions (models, windows, CABs, questions, lockdowns), models of another type or without authorization and conflict exclusion; a change is standard only from a published template; rows hanging off a change need someone who works it, and what is made from a confidential change is confidential. Tests `tests/change-*.test.ts`; the modules together in `tests/integration-modules.test.ts`. Implemented changes move linked incidents on hold «منتظر اجرای تغییر» and problems waiting on a change (`change/linked.ts`); `lockdown_on_major` (off by default) starts a lockdown when a major incident is declared.
- **Service requests and the catalogue** (`docs/modules/request_FA.md`): tables `src/shared/tables/request.ts` (catalogues, categories, audiences, items `ITM` with immutable versions, questions and sets, form policies, task templates, guide rules, settings; carts, `REQ` → `RITM` → `RTSK`, answer facts, `SUB`), pure model `src/shared/request` (order forms, audiences, promises, lifecycle), server `src/server/modules/request` (`installRequestModule()` after the SLA service: lifecycle hooks and roll-ups, the one hook on `"*"` that moves items after approvals; ordering re-checks entitlement, ordering for others and answers on every path, the generic API included; fulfilment through flows bound to the item's code via `startCatalogFlows`, task templates or by hand; seed of the IT catalogue), routes `/request`, UI `src/ui/modules/request` (space «خدمات»; `OrderForm` is the one order-form renderer — the portal embeds it). Answers are split by data class: `answers`, `private_answers` (field group personal), sealed `secret_answers`; never send sensitive or secret answers to a model (`promptSafe`). Records an order makes in another module's table (the «گزارش مشکل» incident, «تبدیل به رخداد») get only choice values that table offers (`offeredChoice`: an order's channel), never a secret or sensitive answer (`openAnswers`). Requester rules follow the row's write mode (`modeOn`: an agent's own order is a requester's), not the area-wide grant (`requesterLike`, creates only); tasks come from the item's group or assignee only; the task assignees of other groups are `fulfillers` (readers: read, never write). A secret field holding structured text takes `hint: false` (no last characters shown). AI plugs in with `registerRequestAi`. An item bound to a service offering (`catalog_item.offering_id`) is for the people the portfolio entitles (`registerOfferingEntitlement`, registered by the portfolio) and each requested item keeps `entitlement`; the order form's assist slot (`request/slots.ts`) takes knowledge's deflection.
- **Configuration management and the service portfolio** (guides `docs/modules/cmdb_FA.md`, `service_portfolio_FA.md`): tables `src/shared/tables/{cmdb,service_portfolio}.ts` (the CSDM class pack, relationship types and identification rules in `@shared/cmdb/classes`; pure logic — class tree, impact propagation with weights and redundancy, health, snapshot diff, identifiers, CSV/JSON — in `@shared/cmdb/logic`, the portfolio's status, bars, scores, overlaps and quadrants in `@shared/service_portfolio/logic`; API contracts `@shared/{cmdb,service_portfolio}/api`), servers `src/server/modules/{cmdb,service_portfolio}` (installed after incident/problem; the portfolio after the CMDB: services and offerings are CIs), routes `src/server/routes/{cmdb,service_portfolio}.ts` (+ the public status page `GET /api/v1/status/:key` on `publicApiRoutes`), UI `src/ui/modules/{cmdb,service_portfolio}` (spaces «پیکربندی» key `assets` — ITAM joins it with `spaceKey` — and «سبد خدمات»; the map is @xyflow/react + dagre in `cmdb/ServiceMap.tsx`), tests `tests/cmdb-*.test.ts`, `tests/service_portfolio-*.test.ts` (`tests/cmdb-helpers.ts` builds an organisation with every relevant role). Reads of the two modules go through the incident module's `liveRows`/`liveRow` (re-exported by `modules/cmdb/common.ts`); conditions may name the record id (`{ f: "id", op: "in", v }`, `condField`/`idField` of `@shared/model/conditions`). Maps and impact compute with system rights and show only readable CIs (placeholders, counts). The CMDB is the change module's impact provider (`modules/cmdb/change.ts`: impacted services, related-CI conflicts, owners for «service_owner»). Extension points: `CiPicker` (registered with `registerRefPicker("ci")` of `src/ui/records/extensions.ts`, so every CI field uses it) and the «پیکربندی و اثر» panel (every table with `ci_id`), `impactAnalysis`/`servicesImpactedBy`/`dependencyMap`/`createOrUpdate`, `servicePicker`/`entitledOfferings`/`myServices`/`refreshStatuses`, the participant source «service_owners» and approver sources `service_owner`/`service_change_approvers`, `registerCmdbAi`/`registerPortfolioAi`. Fields a module stamps from a service or a job are `system` when they are bookkeeping (the review marker, the public key) — dropped from user input, set by trusted writes (`{ trusted: true }`) — and `readonly` when people see them as part of the record.
- **Knowledge management** (guide `docs/modules/knowledge_FA.md`): tables `src/shared/tables/knowledge.ts` (bases with audiences and contributors, category tree, articles whose content changes only through `kb_version` drafts → review/approval → publication, templates, feedback, knowledge tasks with an SLA, snippets, blocks, glossary, subscriptions, read-and-acknowledge campaigns, KCS licences, AQI reviews, gaps, duplicates, search rules, decision trees, domains, settings); the event stream `sm_kb_events` is a local runtime table. Row rules test the row's **own columns only**: audiences and contributors are compiled onto rows (`c_*`, `r_units`, `x_units`, `k_users`/`k_groups` — `modules/knowledge/contrib.ts` fills them in hooks and propagates changes with the job `kb.contrib`), because a dot-walked group test (`base_id.k_groups in_my_groups`) of a member without groups compiles to `false` but keeps the walk's parameters (an engine bug PostgreSQL refuses). Server `src/server/modules/knowledge` (`installKnowledgeModule()` after the RAG index): Persian search (`search.ts`, SQL twin of `searchForm`, glossary, rules, semantic fusion with `retrieve`), the reading view (`render.ts`), versions and approvals («یک تأییدکننده کافی است» = the first answer decides), KCS capture and WIP, quality sweep `kb.sweep`; articles and snippets are RAG sources with an AI-channel rule, so AI answers follow reading access exactly. UI `src/ui/modules/knowledge` (space «دانش»: home with `AskPanel scope={{ tables: ["kb_article"] }}`, search, reader at `kb/a/:id`, editor at `kb/edit/:version`, workspace, dashboard; the «دانش» side panel registers on `"*"` for task-like tables with links). Linking articles to records needs someone who works the record (`requesterOnly` is refused). - **Performance at scale** (docs/PERFORMANCE_FA.md; sizing for banks in docs/SERVER_FA.md §3). Invariants:
  - *Filter-mode predicates with SQL/JS parity:* the access predicate and `toSql(…, { filter: true })` emit plain comparisons (a NULL is as good as false in a WHERE) so indexes answer them — compile a condition you only filter with in filter mode, never wrap index columns in functions, and keep `evaluate` (JS) and `toSql` giving the same answer (`tests/engine-conditions.test.ts`). Participant sources implement `tables()` (the provider leaves out sources that name no row of a table this request).
  - *Search:* numbered tables keep a stored `search_<hash>` document (generated column + trigram index where `pg_trgm` exists) of the search fields **every reader may see** (`storedSearchFieldsOf`: no field-group fields); fields of a field group are searched on their own columns, only for callers who see them (`searchSql`, `tests/engine-search-groups.test.ts`).
  - *Lists:* keyset pagination (`after` cursor) and counts capped at `COUNT_LIMIT` (10 000) — never OFFSET deep pages or unbounded `count(*)`.
  - *Writes:* no organisation-wide lock (round 3, PERFORMANCE_FA.md §۱۴). Sync revisions are transaction ids (`pg_current_xact_id()`), pull cursors and «زنده» tokens are snapshots (`src/server/sync/snapshot.ts`: `deltaSql`, `currentSnap`); never read `sm_org_sync.rev` as a counter or compare revisions with `>` (use snapshot visibility; a changed row is one whose revision differs). A record's writes queue on its row (`for update`), derived values recompute in `onBeforeCommit` work (advisory lock per key). `sm_org_sync` keeps the organisation's sync `epoch` (`bumpSyncEpoch`: restores, xid regression) and `purged` watermark. `ITSM_SERIALIZE_WRITES=1` brings the old lock back (fallback; `ensureOrgLock`/`late` only matter then). Write admission (`admitWrite`): at most `writers_per_org` (kariz.json; env `ITSM_WRITERS_PER_ORG` wins; default 3) write transactions of an organisation per process in the database — a throttle. The lock probe (`db/lockprobe.ts`, `setLockProbe`, off in production) measures what still takes `lockOrg`.
  - *Notifications:* a rule's event fans out through `notify.batch` (per-person rendering outside the transaction, one short write per chunk for the bell rows) and `notify.send` jobs per channel. Large groups: «خودکار» notifies only the leads and the manager of a group over `LARGE_GROUP` (50) members — every member again when it has neither (`groupAudience`, warned on the group form by `groupNotifyWarning`); a rule's `large_groups` overrides the group's `notify_mode`.
  - *«زنده»:* `GET /o/:org/pulse` is scoped (tables `t`, records `r`, `since`), goes through `loadOrg` (`guardOrgSession`) and is always a background request (`isBackgroundRequest`): it never refreshes `last_seen_at`, so the idle timeout still ends an abandoned screen.
  - *Archival:* closed records untouched for N years move to `<table>_arc` (`engine/archive.ts`), readable read-only under the same read rule (`requireReadable(…, { archived: true })`) with their journal, history and attachments (downloads through `blobStore(cfg)`); backups include the `_arc` tables (`pg_dump` of the whole database) and every blob.
  - *Server edition tuning:* ONE source, `src/server-edition/pgtune.ts` (`tunePostgres`, `recommendedWorkers` = max(2, min(12, round(cpus/3))), `recommendedPool` = 10 on 8+ cores else 8, `connectionsFor` = workers × pool + 30, at least 50, keeping workers × (pool + 1) + 1 ≤ max_connections − reserve); `scripts/pg-local.mjs` loads it. The job runner ticks only on the scheduler leader with `concurrency: JOB_CONCURRENCY` (4). The server edition's pools use prepared statements (`createPostgresDb({ prepare: true })`); the web runtime keeps `prepare: false` (Supabase's transaction pooler). `bootstrapDatabase` creates `pg_trgm` and `pg_stat_statements` (`SERVER_EXTENSIONS`).
  - Measure with `scripts/pg-local.mjs` (a tuned local cluster), `seed-bank.mjs`, `serve-pg.mjs`, `loadtest.mjs` and `explain-bank.mjs` on a real PostgreSQL (docs/PERFORMANCE_FA.md §12).
